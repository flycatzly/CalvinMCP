# 回复风格：是否需要回，以及怎么回

回复建议的目标是「像用户本人在这个会话里会发的话」，不是一封完整商务邮件。顺序永远是：**先解决要不要回，再解决回什么，最后才解决写多长**。

对应工具：wai_reply_draft（参数 name、limit、styleDays、minimumChatMessages、selfName、out）。上下文来自 wai_person、wai_chat_history、wai_contact_daily；本人昵称由 wai_profile_init 的 ownerAlias / ownerAliases 配置。

## 1. 是否需要回复

1. 读取当前联系人的最新上下文（默认近 120 条，limit 可调）。
2. 忽略系统消息（撤回、入群提示、转账到账等）。
3. 检查最后一条**对话**消息是谁发的：如果最后一条是本人发的，默认不追发——除非对方之后又问了一句。
4. 判断对方最后一条是否只是自然收尾：「好的、收到、谢谢、哈哈、表情、OK」这类通常不用回。
5. 识别唯一需要回应的问题、请求或情绪。一次只解决一个核心点，不复述整段背景。
6. 只有存在**实质不同的决策分支**时才给一个备选（例如「报价待定 vs 明确报价」），否则只给一条主草稿。

不需要回复时直接给结论，不要硬凑一句：

    不用再回。你已经回复过，等对方下一条。

需要回复时给一条主草稿 + 一句判断：

    建议回：
    > 好的，我这边今天下午把初稿发你，最晚明早。

    判断：熟悉的合作对象；回应交付时间；金额与排期待你确认。

## 2. 一条主草稿的形态

- 一条主回复，通常 1–2 个微信气泡。超过 2 个气泡时先删掉解释性内容。
- 长度优先贴近用户本人的滚动样本（近 30 天跨联系人私聊的聚合长度）；样本不足时默认不超过 50 个中文字。
- 先直接回答，再补一个必要的问题或下一步。
- 少用句号和完整书面段落；标点、语气词、表情、英文缩写的使用取决于当前会话证据。
- 不重复对方已经知道的方案、背景与理由。
- 群里回复要考虑旁观者与责任归属，不把适合私聊的亲昵称呼带进群里。
- 用户明确要完整报价、合同边界、交付说明或正式邮件时，才展开长版（并说明这是长版）。

## 3. 六种关系语域

| 语域 | 判定线索 | 写法 |
| --- | --- | --- |
| 亲近朋友 | 长期私聊、互相起外号、常有表情与缩写 | 沿用双方已有称呼与语气；可以轻松，但不突然油腻或煽情 |
| 熟人 / 同辈 | 有来有往、语气平稳 | 直接回答，省略公文式开场与结尾 |
| 熟悉的合作对象 | 有历史合作、聊过具体交付 | 保留日常语气，同时把金额、时间、下一步说清楚 |
| 新商务联系人 | 首次或极少对话、身份明确但关系浅 | 礼貌中性，一次只问必要信息，不堆完整服务介绍 |
| 客户 / 上级 / 老师 | 对方身份高于我方或存在服务关系 | 尊重但具体；只有该会话原本常用「老师」时才沿用 |
| 群聊 | 多人群、有旁观者 | 简短、可公开、不替别人承诺、不泄露私聊信息 |

关系不是固定标签：优先使用当前会话近 30–80 条双方消息；长期总体习惯只决定长度、分段与标点，不覆盖当前关系。

## 4. 只学习什么

**跨联系人样本（近 30 天本人发出的私聊文本）**：

- 只统计长度、分段习惯、标点习惯（是否用句号、是否用空格）。
- 覆盖不同关系的普通联系人，不只看重点标签里的商单与推广对话。
- 排除群聊、链接正文、附件占位、转发和复制的长文。

**当前联系人样本（当前会话）**：

- 学习称呼、确认词、笑声写法（哈哈 / hh / 笑死）、口语词、英文混用与表情。
- 该会话至少有 5 条本人消息（minimumChatMessages）后才采用专属口语。
- 样本不足时保持中性，并说明「样本不足，未模仿专属语气」。

**不学习、不外传**：

- 不把原始私聊复制进报告、技能包、外部系统或模型服务。
- 不把某一个人的说话方式套到另一个人身上。
- 数据变化时按滚动窗口（默认 30 天）刷新，只保留聚合指标。

## 5. 禁用套话

以下表达默认禁止，除非用户明确要求正式版：

- 「老师你好，收到」「收到，我这边同步一下」。
- 「我会结合前面的上下文」「为了避免口径偏差」「为了确保信息准确」。
- 「有需要补充的信息我会集中列出」「如有疑问随时沟通」。
- 「根据您的要求」「综上所述」「特此回复」。
- 「感谢您的信任与支持，期待与您合作」（首次私聊且无历史时尤其禁止）。
- 任何把一两句微信扩写成方案书、报价单或服务介绍的写法。

## 6. 事实闸门

金额、日期、交付范围、授权、付款、完成状态与对外承诺必须来自原消息或用户确认。无法确定时，指出缺哪一个事实：

    建议回：
    > 这个我明天上午给你确认下价格，其他没问题。

    判断：熟悉合作对象；排期已定；**价格待你确认**（原消息未给金额，草稿里不写数字）。

禁止：

- 编造报价、折扣、名额、档期、案例、关系或授权。
- 用「大概」「应该可以」替用户做出承诺。
- 把「待核实」的附件内容当成已知事实写进话术。

## 7. 默认输出块

    建议回：
    > 一条可直接发送的短回复

    判断：<关系语域>；<回应什么>；<哪些事实待用户确认>。

可选补充（只在有用时给）：

- 备选：仅当存在实质不同的决策分支。
- 不用回的理由：当结论是不需要回复时。
- 样本说明：当本会话样本不足 5 条本人消息、或未配置本人昵称时。

绝不出现：发送按钮、定时发送、「已发送」之类的表述。草稿只存在于本机，发送动作永远由用户本人在微信里完成。

## 8. 常见错误对照

| 错误写法 | 问题 | 改法 |
| --- | --- | --- |
| 「收到，我会尽快处理」 | 没有信息量，对方仍不知道时间 | 「今天下班前给你初稿」 |
| 「这个价格我们可以再谈」 | 替用户让价，属于越权承诺 | 「价格我确认后回你」 |
| 「你之前说的那个方案我看过了」 | 复述背景，浪费一条气泡 | 直接给结论或问题 |
| 一条 200 字的消息 | 微信阅读体验差，也不像本人 | 拆成 1–2 个气泡，删掉解释 |
| 在群里说「咱俩私聊」 | 把私聊关系带进公开场合 | 直接私聊对方，不在群里点名 |
| 「老师你好」开头（首次商务） | 若该会话从不这么叫，就显得模板化 | 用「你好」或直接说事 |
| 把待核实的金额写进草稿 | 事实闸门失守 | 写成「价格我确认后回你」 |

## 9. 群聊回复的额外约束

- 考虑旁观者：群里说的每句话都会被其他成员读到，可能被截图转发。
- 不替别人承诺：不写「我们都会配合」「团队没问题」，除非用户确认。
- 不泄露私聊信息：不把 A 私聊里的话在群里复述给 B。
- 不点名施压：需要催某人时优先私聊，群里只做进度同步。
- @ 的使用要谨慎：只在必须让对方看到时使用，不滥用 @所有人。

## 10. 语气细节的使用准则

| 元素 | 何时用 | 何时不用 |
| --- | --- | --- |
| 表情 / 表情包 | 当前会话历史里本人经常用 | 首次商务、客户/上级、严肃话题 |
| 「哈哈 / hh / 笑死」 | 对方也这么用，且话题轻松 | 对方在谈时间、金额、风险 |
| 英文缩写（ok / thx / btw） | 双方历史里出现过 | 对方全程中文且正式 |
| 语气词（哈、呀、啦、～） | 亲近或熟人语域 | 新商务、客户/上级 |
| 句号结尾 | 需要显得确定时 | 轻松对话里会显得生硬 |

判断标准只有一个：**当前会话里本人是否这么说过**。没有证据就保持中性。

## 11. 用户纠正之后的调整

- 用户说「太正式了」「不像我说话」：降低书面度，删掉开场与结尾，缩短到 1 个气泡。
- 用户说「太随意了」：去掉表情与语气词，补上明确的时间或下一步。
- 用户改了金额或日期：以用户给的为准写回草稿，并记下这是人工确认过的事实。
- 用户说「这条不用回」：把它当作对「是否需要回复」判断的反馈，后续同类收尾语默认判为不需要回复。
- 反复出现的纠正（例如总是把某个中间人判断成品牌方）应通过 wai_feedback_add 持久化，而不是每次在对话里重新解释。
