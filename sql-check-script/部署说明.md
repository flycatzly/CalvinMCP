## 完整自然语言使用示例（全部能力覆盖）

直接对 AI 说需求即可，无需记命令。三条纪律贯穿全部示例：**仅只读**（只做 SELECT/WITH/SHOW/DESCRIBE/EXPLAIN，永不写库）、**先审后执行**（任何 SQL 先展示给你、你确认后才执行，你不回复就等待）、**脱敏**（手机号/身份证/邮箱等敏感字段自动脱敏或排除，样例只给 ID 不出明文）。另外：预计结果 > 5000 行先 COUNT 再抽样；跨 PRE/UAT 取证前二次确认环境；拿不到证据输出「待补充信息」、结论标「待验证」，禁止猜根因。

每条示例 = 一句可直接照说的话术「…」+（背后调用的能力/工具）+ 一句话得到什么；每个细分能力恰好一条，场景全集只在本节展开（README 为速查表）。

### 模块 · 模式A 全链路检测

#### A1 项目探查与取证

**A1-1 项目代码 SQL 提取与调用链定位**

> 「帮我扫一遍 D:\proj\order-service 里的 SQL，把每条 SQL 的文件位置、调用链（Controller → Service → Mapper）和涉及表都找出来，做成 SQL 清单」

- **背后调用**：`workflows/01_项目SQL探查.md` 全链路起点——按技术栈扫 SQL 落点（MyBatis `*Mapper.xml` 与 `@Select/@Update/@Insert/@Delete`、JPA `@Query/@NamedQuery/nativeQuery`、Spring `JdbcTemplate/NamedParameterJdbcTemplate`、Go `db.Query/Exec/Raw` 与 gorm `Raw`、Python `execute(/text(`、Flyway/Liquibase `*.sql`、datasource url 配置）+ `list_tables`（`name_like` 过滤）/`describe_table` 反查补齐高频/大表命中与预估行数
- **得到什么**：`outputs/SQL清单_<项目>_<日期>.md`——每条 SQL 的 文件:行、脱敏 SQL、调用链、涉及表、数据源、风险初判，作为八步分析与巡检报告的输入。

**A1-2 批量 Mapper 扫描与风险分级入队**

> 「Mapper 里这几个查询都说很慢，帮我按风险等级排个巡检清单：命中风险信号的做完整检查，没命中的抽样看」

- **背后调用**：`01_项目SQL探查` 风险初判（对照 `references/sql_risk_signals.md` 12 条高危信号，只标命中哪几条、不下最终结论）+ `workflows/sql_check_workflow.md` 批量处理策略（P0/P1 候选做完整八步 + EXPLAIN 取证；P2 候选只做静态信号 + 抽样 EXPLAIN；单次巡检覆盖全部 P0/P1 + 30% P2）
- **得到什么**：分级巡检清单（每条命中哪几条风险信号、入队优先级、覆盖度口径）。

**A1-3 数据源定位与库表反查**

> 「帮我确认测试订单库连的是哪个数据源，列出库里跟订单、支付相关的表；另外我只知道有个字段叫 mobile，帮我找出哪些表有这个字段」

- **背后调用**：`find_database`（参数是 `name`，大小写不敏感子串；`probe: true` 测可达）/`list_sources` 定位 source id；`list_tables`（`name_like` 过滤 + 注释 + 预估行数）；`find_tables_by_column`（按列名关键字反查表，表结构未知时定位）
- **得到什么**：source id + 目标表清单（预估行数/注释）+ 按列反查的候选表；后续所有取证工具都传同一 source。

**A1-4 真实库取证（表结构/索引/执行计划/数据量/质量）**

> 「检测前先把证据取齐：order_info 的真实字段和索引、这条 SQL 的执行计划、表里现在多少行，再抽几条看看有没有脏数据」

- **背后调用**：`describe_table`（真实列/主键/索引/注释/预估行数，防幻觉 SQL）；`query` 跑 `EXPLAIN <sql>` 与 `query_plan` 显式执行计划（仅接受 SELECT/WITH，构造前即拒写语句）；`count_rows` 精确行数（`total` 为字符串型 bigint）；`sample_data`（limit/where/order_by 抽查脏数据/异常值，敏感列按白名单脱敏后展示）
- **得到什么**：证据包（结构 + 计划 + 数据量 + 样本），每条风险结论都能标注证据来源（EXPLAIN / describe_table / count_rows）。

**A1-5 WHERE 条件区分度与列画像取证**

> 「看看 status 这个字段的取值分布和区分度，再给我 user_id 这列的画像：空值多少、去重多少、极值多少」

- **背后调用**：`distinct_values`（Top-N 取值分布 + 精确 `distinct_total`）；`column_stats`（stats 六字段 row_count/non_null/distinct_values/min_value/max_value/avg_value）；`count_rows`（`where` 单值精确计数，一次只接一个条件，不逐值拼分布）；`query` + `GROUP BY`（占比与多列交叉分布）
- **得到什么**：区分度结论（某取值占比 > 50% → 区分度低，单用它过滤价值有限）+ 列画像（空值率/去重数/极值）。

**A1-6 多方言执行计划判读**

> 「这条 SQL 在 MySQL 和 PostgreSQL 上的执行计划分别怎么读？把两边的全表扫描、排序、索引命中形态都对上」

- **背后调用**：`query` 跑 `EXPLAIN`（MySQL）/ `EXPLAIN (FORMAT JSON)`（PG）+ `references/calvin-db-mcp工具映射.md`「方言适配」与 `references/sql_risk_signals.md`「方言实测注记」（`type=ALL`↔`Seq Scan`、`Extra=Using filesort`↔`Sort` 节点、`Extra=Using temporary`↔`HashAggregate`、`type=ref/eq_ref`↔`Index Scan/Index Only Scan`、复合索引免排序↔`Backward index scan`/`Index Scan Backward`；OceanBase 走 MySQL 模式按 MySQL 列判定）
- **得到什么**：双方言计划判读结论（含「命中索引字段 ≠ 一定走索引、以实测计划为准」判读注记）。

#### A2 风险专项检测

**A2-1 单条 SQL 风险检查（全链路八步）**

> 「帮我检查这条 SQL 的风险：SELECT * FROM order_info WHERE status=1 ORDER BY create_time DESC LIMIT 100000,20」

- **背后调用**：`workflows/sql_check_workflow.md` 八步证据版（禁止跳步）：Step 0 取证 → Step 1 风险识别（对照 `sql_risk_signals.md` 逐条列命中项并标证据来源）→ Step 2 where 条件分析 → Step 3 索引判断 → Step 4 慢查询判断 → Step 5 join 风险 → Step 6 order by 风险 → Step 7 风险输出（每行附证据）→ Step 8 优化建议；输出按 `outputs/SQL 检测输出格式.md`
- **得到什么**：逐项风险表（风险类型/风险原因/影响范围/可能表现/验证方式证据/风险等级）+ 至少 3 条优化建议。

**A2-2 深分页专项**

> 「重点看深分页：LIMIT 100000,20 这种大偏移翻页到底有什么风险，给我证据和改法」

- **背后调用**：高危信号 #6 深分页（默认 P1）+ `query` 跑 EXPLAIN 取 `rows`/`Extra` + `count_rows` 对比真实数据量算扫描行数比（EXPLAIN rows ÷ 返回行数；> 100 → P1、> 1000 → P0 候选）+ 深分页排序代价证据判定（filesort/TEMP B-TREE/Sort 形态）
- **得到什么**：深分页风险判定（附扫描行数比证据）+ 优化建议（改哪里+查哪里+验证哪里，附 EXPLAIN 前后对比预期）。

**A2-3 索引缺失/失效专项**

> 「这条查询说很慢，帮我查索引到底是缺失还是失效了——是不是函数包了字段、隐式类型转换、前缀模糊导致没走索引」

- **背后调用**：Step 3 索引判断（`describe_table` 真实索引列表直接判命中/未命中，where/join/order by 字段与索引左前缀比对）+ 高危信号 #2/#3/#4/#5（无 where 或字段无索引、`like '%关键词%'` 前缀模糊、函数包裹索引字段 `date(create_time)`、字符串列传数字隐式转换）+ `query` EXPLAIN 看 `key=NULL`/`type=ALL`
- **得到什么**：索引缺失 vs 失效结论（附 EXPLAIN 证据）+ 建索引 SQL **建议**（本 Skill 不执行 DDL，交 DBA 评估，附改后预期与大表锁表/在线 DDL 风险提示）。

**A2-4 慢查询排序与分组专项**

> 「这条慢查询是不是排序拖慢的？ORDER BY、GROUP BY 有没有走索引，filesort 和临时表的代价有多大」

- **背后调用**：Step 6 order by 风险（EXPLAIN `Extra` 是否 `Using filesort`）+ 高危信号 #9/#11（`group by` 大表 `Using temporary`、order by 未命中索引大结果集）+ `count_rows` 取排序前数据量 + 方言判读（PG `Sort`/`Sort Key:`、`HashAggregate`）
- **得到什么**：排序/分组风险判定（filesort/临时表证据 + 排序前数据量）+ 排序索引优化建议。

**A2-5 JOIN 链路专项**

> 「这条多表 JOIN 慢，帮我把关联链路查清楚：外键关系、两侧关联字段有没有索引、是不是大表直接 join 没先过滤」

- **背后调用**：`fk_relationships`（外键关系清单，join 链取证）+ `describe_table`（关联字段两侧索引）+ `query` EXPLAIN（两侧 `rows`、大表 join 成本）+ Step 5 join 风险（先过滤再 join、两侧索引）
- **得到什么**：JOIN 链路风险判定（关联链 + 两侧索引证据 + 两侧扫描行数）+ 改写建议（如先过滤再 join）。

**A2-6 SELECT * 与返回字段过多专项**

> 「帮我看看这条 SELECT * 有什么问题，实际只需要哪几列，有没有可能走覆盖索引」

- **背后调用**：高危信号 #1 `select *`（默认 P2）+ `describe_table` 比对实际所需字段 + 覆盖索引判定（`Extra=Using index` / `Index Only Scan`；可用覆盖索引未用 → P2）+ 证据优先降级原则（实测已走索引、rows 很小则降 P2 并注明「实测无性能影响」）
- **得到什么**：字段裁剪建议（保留列清单）+ 覆盖索引可行性结论。

**A2-7 大结果集 / 无 LIMIT 列表查询专项**

> 「这个列表查询没有 LIMIT，会不会一次拉全表？帮我评估返回行数风险，超过 5000 行的给我抽样方案」

- **背后调用**：高危信号 #12 无 LIMIT 的列表查询（P1）+ `count_rows` 先估量 + `query` 自动 LIMIT（`row_count` 为当前可见行数，看 `truncated`）+ 安全规则「预计 > 5000 行先 COUNT 再抽样」
- **得到什么**：结果集规模判定 + 抽样/分页方案（不一次拉全）。

**A2-8 写 SQL 全表覆盖风险静态评估**

> 「代码里这条 UPDATE 没带 WHERE，帮我评估影响面——不执行，只要风险结论和人工修复清单」

- **背后调用**：高危信号 #7 `update`/`delete` 无 where（**P0**）+ 词法守卫口径 + `count_rows` 只读估算命中行数 + 风险等级「写风险优先：涉及 update/delete 的隐患等级不低于同类查询风险 +1 级」；永不执行写操作
- **得到什么**：P0 风险结论（附影响行数证据）+ 核对清单与变更 SQL 供 DBA 人工执行。

#### A3 结论与交付

**A3-1 风险等级判定（P0/P1/P2）**

> 「按 P0/P1/P2 给这批 SQL 定级，每条等级都要有证据；小表或者已经走索引的别虚高」

- **背后调用**：`references/风险等级定义.md`（P0 数据正确性已受损/可致生产事故、P1 性能明显劣化、P2 隐患或写法不规范；扫描行数比 > 100 → P1、> 1000 → P0 候选；小表 < 1 万行索引缺失降 P2；数据一致性类一律 ≥ P1，业务状态错误 → P0）+ 证据优先原则（无证据标「待验证」，不得给确定等级）
- **得到什么**：逐条风险等级 + 业务影响（影响哪个接口/模块/用户），可追溯到具体证据。

**A3-2 优化建议（含索引建议边界）**

> 「给出优化建议：每条说清改哪里、查哪里、怎么验证；要建索引的给我 SQL 但不要执行，附上执行风险提示」

- **背后调用**：Step 8 优化建议（至少 3 条，验证用 EXPLAIN 前后对比）+ 索引建议输出边界（只读不执行 DDL；`ALTER TABLE ... ADD INDEX ...` 以「建议」而非「必须」交 DBA，附改后预期如 `key=idx_status_create_time`、无 filesort，标注大表加索引的锁表/在线 DDL 风险）
- **得到什么**：优化建议清单（改哪里+查哪里+验证哪里）+ 待 DBA 评估的索引 SQL 建议。

**A3-3 项目级巡检报告**

> 「给 D:\proj\order-service 出一份 SQL 巡检报告：风险分布、优化优先级清单，按模板落盘」

- **背后调用**：`outputs/巡检报告模板.md`（风险分布 + 优化优先级清单）+ 批量处理策略覆盖度（全部 P0/P1 + 抽样 30% P2）+ 落盘约定（`outputs/巡检报告_<项目>_<日期>.md` 或你指定路径）
- **得到什么**：巡检报告 .md（风险分布、优化优先级清单、逐条证据与建议）。

**A3-4 发生产前门禁**

> 「这条 SQL 要发生产了，帮我做全链路质量检测当发布门禁，重点看索引和深分页，告诉我能不能发」

- **背后调用**：模式 A 全链路八步（重点 Step 3 索引判断 + Step 6 order by/深分页专项）+ `references/sql_input_contract.yaml` 输入契约（补全 project_path/sql/datasource/source/environment）+ 环境口径（`environment` 须命中 `environment_allowlist`，PROD 默认禁止，只在 TEST/PRE/UAT 取证）
- **得到什么**：发布门禁结论（可发 / 需修复后再发）+ 阻断项清单（每项附证据与修复建议）。

**A3-5 一键巡检（巡检自动化）**

> 「用巡检一键把 assets/sample_sql 里的 SQL 清单跑一遍，出报告骨架并和上轮基线比对」（也可直接跑命令：`node 巡检一键.mjs --source <source_id> --manifest assets/sample_sql/manifest_example.json --baseline-dir <仓外目录> --html --out <仓外路径>.md`）

- **背后调用**：`巡检一键.mjs`（SQL 清单 → 只读预审四门 → EXPLAIN/表行数/脱敏样例并发取证 → manifest.consistency 对账骨架实测 → 按巡检报告模板生成骨架）+ 示例清单 `assets/sample_sql/manifest_example.json`（键形态经 config-lint 契约互证）
- **得到什么**：巡检报告骨架 .md（六节对齐模板，报告头含建议落盘名与增量对比）+ 可选 .html 版 + 基线文件自动刷新（下轮自动出「新增/消除/变化」摘要）；风险判定与优化建议仍留人工（先审后执行）。

### 模块 · 模式B 只读数据分析

#### B1 常用分析

**B1-1 状态分布分析**

> 「分析回归后 orders 表各订单状态的数量分布，看有没有异常堆积」

- **背后调用**：`references/分析模板库.md` §1 状态分布模板 + `describe_table` 取真实 schema（防幻觉字段，SQL 带中文注释标注字段来源）+ `query`（GROUP BY 数量/占比，字段用业务名别名）或 `distinct_values` 快速取分布；**先审后执行**
- **得到什么**：状态分布表（状态/数量/占比）+ 异常提示与业务结论（如「已取消占比 42%，明显高于上版本 18%，建议排查取消/退款流程」）。

**B1-2 两表行数核对**

> 「核对一下 t_order 和 t_order_item 昨天的行数对不对得上，差多少给我精确数字」

- **背后调用**：`count_rows`（带 `where` 时间条件取精确行数；`total` 为字符串型 bigint——比对用 `Number(total)` 或原样字符串比较，防雪花 ID 精度丢失）
- **得到什么**：两表行数比对结论（各自精确行数 + 差值 + 是否一致）。

**B1-3 重复数据检查**

> 「看看 orders 里订单号重复的有多少，只要数量和样例 ID，不要明文敏感信息」

- **背后调用**：`分析模板库.md` §4 重复核查模板（GROUP BY + `HAVING COUNT(*) > 1`）+ `query`；敏感字段**脱敏或排除**（样例输出只给 ID）
- **得到什么**：重复项统计（重复键 + 出现次数 Top）+ 脱敏样例 ID。

**B1-4 空值/缺失核查**

> 「查一下 orders 的关键字段缺失情况：手机号有多少空值、缺失率多少，超过阈值的报给我」

- **背后调用**：`分析模板库.md` §3 空值核查 + §6 判定口径（关键字段缺失率 > 5% 报异常）+ `column_stats`（`non_null` 算空值率）/`query` COUNT 差值
- **得到什么**：缺失统计（总行数/非空/缺失/缺失率）+ 超阈值异常提示。

**B1-5 异常值/脏数据检查**

> 「帮我做一次数据质量检查：创建时间在未来的、金额为负的、status 出现未定义值的各有多少，再抽几条脏数据样例」

- **背后调用**：`分析模板库.md` §6 数据质量（未来时间 `created_at > NOW()`、负数金额、枚举越界 `NOT IN`）+ `sample_data`（limit/where 抽查，敏感列脱敏后展示）；判定口径：未来时间/负数金额/枚举越界一律报异常（P1+）
- **得到什么**：三类异常条数 + 脱敏脏数据样例 + 异常清单。

**B1-6 时间区间趋势（环比按天）**

> 「按天看最近 7 天的订单量趋势，和上一周对比环比变化，标出异常的日子」

- **背后调用**：`分析模板库.md` §2 环比对比模板（`DATE(created_at)` 分组 + 时间区间过滤，注意方言差异：MySQL `INTERVAL 7 DAY` / PostgreSQL `INTERVAL '7 days'`）+ `query`
- **得到什么**：按天趋势表（日期/当日数量）+ 环比异常日标注。

**B1-7 多表状态一致性比对**

> 「帮我查支付流水和订单状态对不上的：支付成功但订单还是未支付的，列出来给我异常订单样例」

- **背后调用**：`references/sql_incident_patterns.md` §2 一致性比对脚本模板（pay_flow JOIN order_info 状态比对）+ `query`（跨表关联）/`fk_relationships`（关系确认）+ 风险等级口径（多表状态不一致 → P0）
- **得到什么**：异常订单列表与样例（订单号/两侧状态/金额）+ P0 风险定级。

**B1-8 多库对比（测试库 vs 影子库 / PRE vs UAT）**

> 「对比 PRE 和 UAT 的 order_info 状态分布，看发版前后有没有漂移；同实例的测试库和影子库订单量也对一下」

- **背后调用**：`find_database` 分别定位两个 source（跨实例分别执行后报告中对比）或同实例 `库名.表名` 跨库（`分析模板库.md` §8 多库对比）+ `query`/`count_rows`；跨 PRE/UAT 取证前**二次确认环境**
- **得到什么**：两库/两环境对比表（差异 + 漂移结论）。

**B1-9 接口前后对比（版本间数据变化）**

> 「对比新旧版本上线前后两个时间窗口的订单量，看新版本有没有少写/多写数据」

- **背后调用**：`分析模板库.md` §9 接口前后对比模板（`CASE WHEN created_at >= ...` 时间窗口分组）+ `query`
- **得到什么**：版本间数据量对比（新旧窗口订单数 + 差异结论）。

**B1-10 日志排查异常刷量**

> 「查一下 user_action_log 最近 7 天单用户单日操作次数 Top，超过 1000 次的列出来，看有没有异常刷量」

- **背后调用**：`分析模板库.md` §10 日志排查模板（user_id × 日期 GROUP BY + `HAVING COUNT(*) > 1000`）+ `query`（时间区间方言写法同 B1-6）
- **得到什么**：刷量嫌疑清单（脱敏用户 ID + 操作次数 Top）。

**B2-1 脱敏取数（样例 ID 不出明文）**

## 一、这个包是什么

- **双模式 Skill**：模式 A SQL 全链路质量检测 / 模式 B 只读数据分析（`SKILL.md` 为入口，双层写库护栏内置）
- **随包自验收**：`tests\fullchain_test.mjs` 全链路 E2E（核心 93 项）+ `tests\run_all.mjs` 一键合并裁决
- **依赖本地 MCP `calvin-db-mcp` v1.6.37**（16 工具，MySQL/PostgreSQL/OceanBase(MySQL模式)/SQLite）——两个包同级放置时，验收与 E2E 自动发现，无需配置路径

### 纯净包（分发包）里有什么（和没有什么）

- 本包**零 npm 依赖**：不需要 `npm ci`、不需要联网；`tests\run_all.mjs` 验收自依赖（selftest 用同级 `calvin-db-mcp`，E2E fixture 用同级 `demo.db` 自供给）
- **不随包**（剔除项）：

| 剔除项 | 说明 |
|--------|------|
| `node_modules` | 本包零 npm 依赖，本来就不需要；MCP 侧依赖由命令生成（见 3.2） |
| 任何 `.` 前缀文件/目录 | `.git`/`.gitignore`/`.zcode` 等一律不随包；`.gitignore` 等由 `calvin-db-mcp` 装机导入 `.dbp` 时自动生成 |
| 开发机路径/临时产物 | 文档与脚本不含开发机绝对路径；`*.log`/`*.tmp`/`thumbs.db` 不随包 |
| 凭据 | 本包从不持有凭据；连接凭据走 `calvin-db-mcp` 的 `.dbp` 导入（`*.dbp`/`dbmcp.config.json` 按敏感文件对待，绝不随包） |

### 自测的三种口径（都是「成功」，别被数字吓到）

| 口径 | selftest | 场景 |
|------|----------|------|
| 未初始化 | 以当日实测为准 | 纯净包刚拷贝、未导 `.dbp`（发布包自验收即此口径） |
| 导入后 | +14 左右（连通性用例解锁） | `install.mjs` 导入 `.dbp` 之后，以实测为准 |
| live 段 | +9（MySQL）/PG 段 | 自动门控（配置有源即跑）或 `FULLCHAIN_MYSQL=1` / `FULLCHAIN_PG=1` 强开 |

**验收线是 0 failed，不是 passed 数**，勿以 passed 数为验收线（用例数随版本/源连通性增长；对方 selftest 双口径两态计数、随版本新钉与源连通性增长，导入 `.dbp` 另有增量钉，均以当日实测为准；计数归属见 `references\验收清单.md` 部署自检 selftest 项「计数归属」注记）。完整判定表见 README「验证装好了」。`run_all` 输出解读示例：

```
RUN_ALL selftest=<p>/<f>[/<s>] sqlite-val=<p>/<f> mysql-val=<p>/<f>[/<s>|off] docsync=<p>/<f> config-lint=<p>/<f> inspect=<p>/<f> e2e=<p>/<f>[/<s>] gates=<...> => OK|SKIP|FAIL
（字段序：selftest=对方自检 · sqlite-val=全工具面活库 · mysql-val=MySQL（off=未开门）· docsync=文档一致性 · config-lint=护栏配置 · inspect=巡检一键CLI门禁 · e2e=核心段(live自动门控) · gates=合并裁决）
（数字以当日实测为准，不写死进文档——对方侧套件随版本增长，硬数字会漂移）
```

live 段纪律：严格只读（information_schema/EXPLAIN 取证类语句）；PRE/UAT 取证前**二次确认环境**；建议 FULLCHAIN_MYSQL_SRC / FULLCHAIN_PG_SRC 显式指定 source id，不靠默认猜源。

## 七、问题排查

| 现象 | 原因 | 动作 |
|------|------|------|
| 客户端技能列表没有本技能 | 目录放错/入口文件名被改/未重启 | 核对 `SKILL.md` 位置与目录名，重启客户端 |
| 工具列表没有 `db` 工具 | MCP 未注册或未重启 | 重跑 `calvin-db-mcp` 的 `install.mjs`（步骤 6 注册）后重启 |
| `list_sources` 返回 `init_required` | 未导 `.dbp` | `node install.mjs <你的.dbp>` |
| 工具无响应且服务端 stderr 有 `enc 解密失败` | `DBMCP_MASTER_KEY` 未设/错钥/密文篡改（启动期 fail-fast 拒启，非工具级报错） | 核对客户端注册 JSON `env` 块的 `DBMCP_MASTER_KEY`（≥8 字符）与密文来源后重启；旧 `enc:` 格式不需要主密钥 |
| `run_all` → `FAIL` 且 selftest 非 0 failed | 依赖/环境问题 | 先 `calvin-db-mcp\mcp` 下 `npm ci --omit=dev` 再复跑；仍失败看 selftest 输出 |
| `run_all` → `FAIL` 且 e2e 非 0 failed | 链路/fixture 问题 | 确认同级 `calvin-db-mcp\mcp` 存在且 `demo.db` 在 `calvin-db-mcp\` 下（fixture 自供给）；看 E2E FAIL 段 |
| E2E 整段 SKIP（0 passed, 0 failed） | demo fixture 双缺（配置无 demo 源且无 `demo.db`） | 保留同级 `calvin-db-mcp\demo.db` 即可 |
| `node tests\run_all.mjs` 报「未找到 selftest」 | `DBMCP_MCP_DIR`/同级布局未指向真实 `mcp` 目录 | `node tests\run_all.mjs <mcp目录>` 显式传参 |
| 工具返回报错带全码 `Error: [E_CODE:retry] 消息` | 按错误码归类（参数/配置/安全红线/驱动透传/限额） | 按报错码反查 `references\故障处理.md`「五、错误类矩阵实测表」：触发条件/实测文案/重试语义/排障方向一表速查 |

现象级问题（慢查询/深分页/锁等待等分析场景）见 `references\故障处理.md`；SQL 风险判定见 `references\风险等级定义.md`。

## 八、升级与版本纪律

**升级**：新包覆盖拷贝到技能目录（先删旧目录再拷，避免旧文件残留）→ `calvin-db-mcp` 侧按其部署说明升级 → 重启客户端 → `node tests\run_all.mjs` 全绿即完成。

**版本纪律**（见 README「版本与文档同步规范」）：每次更新版本（含版本说明）必须同步落到全部对应文档——版本标记行全量对齐、版本说明唯一落点 README「更新记录」、`calvin-db-mcp` 依赖版本引用同步、`run_all` 全绿后才可发布/重打发布包，缺一处即视为发版未完成。

## 九、卸载与清理

1. 删除技能目录（`...\skills\sql-check-script`）
2. MCP 侧卸载/回滚见同级 `calvin-db-mcp\部署说明.md`「升级、卸载与回滚」（含客户端配置回滚 `.bak`）
3. 本包无运行期落盘产物，无需额外清理

## 发版门禁（发版者）

发版 = 跑 `node distribute.mjs --force`，收尾自动「一次性副本验收 + 终态哈希终查」（加固 H19，发版不可能忘）：

1. 纯净打包（逐文件哈希自校验 + 排除项泄漏检查）；
2. **一次性副本验收**：临时目录副本内**同级拷入 `calvin-db-mcp`**（`tests/run_all.mjs` 解析同级包）→
   `calvin-db-mcp\mcp` 下 `npm ci --omit=dev` → 跑 `tests\run_all.mjs`，验后整目录删除——交付树自始至终不进套件；
3. **终态哈希终查**：门禁前后交付树哈希逐位一致 + 纯净复扫。

验收退出码契约（统一诚实 SKIP 口径）：`exit 0` 全部通过 / `exit 1` 存在失败 / `exit 3` 诚实 SKIP
（`run_all` 汇总口径：`OK|SKIP|FAIL`，SKIP 明示记录判过、不冒充全绿）。门禁失败退出码 3、发布包不可交付。
`--gate-only` 只跑门禁不打包（源树口径：源树排除名单内残留——`.git` 等——记「已知排除项（不随包）」
不判红，交付纯净由 `--force` 打包自校验与纯净复扫保证）；`--no-gate` 显式跳过（留痕）。
凭据文件（`accounts.json`）在过滤名单机械兜底，一律不随包。
