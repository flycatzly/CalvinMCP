# 风险等级定义（P0 / P1 / P2 判定标准）
> 版本 v1.4.3 · sql-check-script · 更新记录见 README.md「更新记录」

所有输出中的风险等级**必须按此表判定**，禁止自定义。先判「数据正确性 / 生产事故」，再判性能。

| 等级 | 判定标准 | 典型场景 | 响应要求 |
|------|----------|----------|----------|
| **P0** | 数据正确性已受损或随时可能受损；可导致生产事故 | ① 多表状态不一致（支付成功但订单未支付）② update/delete 无 where（全表覆盖风险）③ 唯一约束缺失导致重复数据 ④ 全表扫描打满 CPU 致接口整体不可用 | 立即上报，给修复方案 |
| **P1** | 性能明显劣化，已影响用户或随时可能超时 | ① EXPLAIN `type=ALL` 全表扫描 ② 大表 join 无过滤 ③ 索引缺失致扫描行数 >> 返回行数 ④ 深分页 | 本迭代内修复 |
| **P2** | 存在隐患但当前影响有限，或写法不规范 | ① `select *` ② 可用覆盖索引未用 ③ `like '%x%'` 前缀模糊 ④ 排序未命中索引但数据量小 | 排期优化 |

## 判定细则

- **数据一致性类一律 ≥ P1**；导致业务状态错误（资金 / 订单状态）→ **P0**
- **扫描行数比** = `EXPLAIN rows` / 实际返回行数：> 100 → P1；> 1000 → P0 候选
- **表规模修正**：小表（< 1 万行）的索引缺失降级为 P2
- **写风险优先**：涉及 update/delete 的隐患，等级不低于同类查询风险 +1 级
- 每个等级必须附**业务影响**（影响哪个接口 / 模块 / 用户）

## 判定原则：证据优先于静态规则

- **实测证据覆盖静态信号**：若 EXPLAIN 显示 rows 很小、已走索引，则即使静态命中 `select *` 等信号，也降级为 P2 并注明「实测无性能影响」
- **反之**：静态无信号但 EXPLAIN 显示大表 `type=ALL`，一律按 P1 处理
- 所有等级都必须可追溯到**具体证据**；无证据 → 标「待验证」，不得给出确定等级
