# 团队规范（AGENTS.md 模板）

这个文件回答一个判断题：**这些约定写在哪里，才能让每个人（和每个 agent）在任何任务里都遵守？**

答案：写进项目根的 `AGENTS.md`。个人跑通不难，难的是团队不跑偏；把「无论做什么任务都要遵守」的测试规范写进 AGENTS.md，比在群里反复叮嘱管用。对应工具 `check_standards`。

---

## 1. 可直接复制的 AGENTS.md 片段

把下面整段粘进项目根的 `AGENTS.md`（没有就新建）。这四条是**硬要求**，不随任务类型变化，评审时按这四条对照。

````markdown
## 测试规范（无论做什么任务都要遵守）

以下四条是硬要求，不随任务类型变化。评审时按这四条对照。

### STD001 证据落盘到约定目录

快照、截图、trace、日志一律落到 `.playwright-artifacts/` 的约定子目录
（`snapshots/`、`screenshots/`、`traces/`、`logs/`、`reports/`、`state/`），不散在临时路径。

理由：散在临时路径的证据，评审时找不到；进不了制品库，也就等于没有。

### STD002 回归默认走 CLI + Skill，MCP 只留做探索

长流程回归用 `playwright-cli` 落盘执行（产物进 `.playwright-artifacts/`）；MCP 浏览器工具只用于探索与定位，不用于跑完整回归。

理由：把完整页面状态反复灌进上下文会烧掉大量 Token（官方基准里一个多步骤会话可到 87000+），后面的断言与失败定位会被挤掉；CLI 落盘能省下四倍多。

### STD003 脚本必须先验证通过再保存

生成的用例必须先过静态门禁（`lint_spec` 的 lint ERROR 为 0）并实际跑通，才允许写入仓库。

理由：脚本还没跑通就提交，是这条流程里最容易踩的坑。「先自行验证再保存」是测试规范，不是可选项。

### STD004 快照、截图、脚本都进制品库

CI 产物必须包含快照（snapshot）、截图、trace 与脚本；评审缺陷时直接引用产物路径，不靠口头复述。

理由：哪一步挂了，打开对应文件就能定位，不用重新跑一遍复现。

### 命令入口

```bash
# 跑之前：配置基线是否可信（放最前面，因为它错的时候后面全是白干）
node scripts/check_config.mjs playwright.config.ts

# 合入前：用例静态扫描，ERROR 必须为 0
node scripts/lint_spec.mjs tests/

# 跑之后：失败归因与派活
node scripts/summarize_report.mjs test-results/report.json
```
````

## 2. 四条规范的要求 + 理由（表格速查）

| 编号 | 要求 | 理由 | 违反的典型症状 |
| --- | --- | --- | --- |
| STD001 | 证据落盘到 `.playwright-artifacts/` 约定目录 | 散在临时路径的证据进不了制品库，等于没有 | 评审时问「截图呢」，答「本机跑的时候有」 |
| STD002 | 回归走 CLI + Skill，MCP 只做探索 | 完整页面状态反复灌上下文会烧掉大量 Token，挤掉后面的断言与失败定位 | 长回归跑到一半「撞墙」，模型看不见当前页面状态 |
| STD003 | 脚本先验证通过（门禁 ERROR 0）再保存 | 「还没跑通就提交」是最容易踩的坑，会积累负资产 | 仓库里一批从来没跑通的脚本，全量回归永远带着已知噪音 |
| STD004 | 快照、截图、脚本进制品库 | 有产物就能直接定位，不用重新复现 | 复现一次要半小时，缺陷工单里只有一句「偶发失败」 |

## 3. `check_standards` 会校验什么

`check_standards` 读项目的规范文件并逐条校验覆盖情况。它的行为：

**找文件**：传入路径是文件就直接读；是目录时依次查找 `AGENTS.md`、`agents.md`、`CLAUDE.md`、`claude.md`、`.github/AGENTS.md`，取第一个命中的。都找不到时返回 `NOT_FOUND`，并附上完整模板和落点提示（「建议在项目根创建 AGENTS.md 并写入下面的测试规范」）。

**校验四条**：每条规范有一组可检索的关键词判据，**全部命中才算覆盖**：

| 编号 | 校验的判据 |
| --- | --- |
| STD001 | 文本里出现 `.playwright-artifacts`，并且出现「落盘」或 `artifact` |
| STD002 | 出现 `cli`，并且出现「探索」或 `explore` |
| STD003 | 出现「验证…通过/保存」或「先…验证」形态的表述，并且出现 `lint` 或「门禁」 |
| STD004 | 出现「制品」或 `artifact`，并且出现「快照」或 `snapshot` |

**输出形态**：逐条给出 `[OK]` / `[MISS]`；缺失时同时给出**要求、理由、补法**三段——不是只说「缺一条」，而是说清缺哪条、为什么重要、怎么补。最后给覆盖计数与结论：全部覆盖为 `PASS`，否则 `INCOMPLETE`。

**为什么缺失不阻断流水线**：规范是人的约定，不是代码缺陷，所以 `check_standards` 的 `exitCode` 恒为 0（结论记在 `verdict` 里）。但缺失项会被明确列出来——**沉默的缺失才是最贵的**：一份没人知道缺了什么的规范，比没有规范更危险，因为它给人一种「我们有规范」的错觉。

**用法**：

```bash
# 校验项目根（或指定某个 AGENTS.md）
node scripts/check_standards.mjs .

# 校验结果示例
# [OK  ] STD001  证据落盘到约定目录
# [MISS] STD002  回归默认走 CLI + Skill，MCP 只留做探索
#         要求: 长流程回归用 playwright-cli 落盘执行；MCP 浏览器工具只用于探索与定位，不用于跑完整回归。
#         理由: 把完整页面状态反复灌进上下文会烧掉大量 Token…
#         补法: 补上「回归默认走 CLI + Skill，MCP 只留做探索」：…
# 覆盖 3/4，缺失 1
# 结论: INCOMPLETE
```

## 4. 评审检查点

1. 项目根**有没有 `AGENTS.md`**？（`check_standards` 返回 `NOT_FOUND` 就是没有。）
2. 四条规范**是不是都覆盖**（`verdict: PASS`）？`INCOMPLETE` 时必须按「补法」补上，不许「下次再说」。
3. 四条**是不是都写了理由**？只写禁令的规范没人遵守，写了理由的规范才能说服人改代码。
4. **命令入口是否写进 AGENTS.md**？规范必须能落到一条可执行命令上（`check_config` → `lint_spec` → `summarize_report`），否则它只是口号。
5. 规范里的目录名**是否与实际落点一致**？写了 `.playwright-artifacts/` 就要真的落在那儿。
