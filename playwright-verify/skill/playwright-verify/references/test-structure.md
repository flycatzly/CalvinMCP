# 用例结构与隔离

这个文件回答一个判断题：**这条 `test(...)` 的边界划对了吗？它和别的用例互相污染吗？它有没有偷偷不跑？**

结构问题不会让用例变红，它只会让用例**变绿得没有意义**。对应 `lint_spec` 的 PW002 / PW007（容器排除）/ PW102 / PW103 / PW104，以及配置侧的 `forbidOnly`（`check_config` CFG001）。

---

## 1. 用例边界怎么划

一条用例 = 一条能独立回归的业务主张。三条判据同时成立才算划对：

1. **有独立主张**：一句话能说清「它证明了什么」（见 `assertion-discipline.md` 的交付契约）。
2. **可单独运行**：`test.only` 单独跑它、或在 `--grep` 里选中它，结果必须与整批跑一致。不一致就是它依赖了别的用例的残留状态。
3. **失败位置唯一**：它红了，你能指出是哪一个环节破了。一条用例里塞进「登录→加购→下单→支付→退款」，红了之后你得逐段二分——这已经是调试而不是回归了。

```ts
// ✗ 边界划错：一条用例背了 5 条业务主张，红了无法定位
test('完整电商流程', async ({ page }) => { /* 登录 + 加购 + 下单 + 支付 + 退款 */ });

// ✓ 一条用例一条主张
test('登录：test 环境 u1 能登录成功', async ({ page }) => { /* ... */ });
test('下单：SKU_A 加购后金额为 ¥99.00', async ({ page }) => { /* ... */ });
test('优惠券：COUPON10 使金额变为 ¥89.10', async ({ page }) => { /* ... */ });
```

**为什么宁多条不宁长条**：`summarize_report` 的聚类口径是「一个失败签名 = 一份工作量」。用例越粗，一次失败里混进多个同源/异源问题的概率越高，聚类出来的签名越含糊，派活也就越含糊。

---

## 2. 状态隔离：`beforeEach` 只做「回到起点」

`beforeEach` 的职责是把测试环境推回一个**已知起点**，不是顺手跑一遍业务流程。

```ts
test.describe('购物车', () => {
  let cartPage: CartPage;

  test.beforeEach(async ({ page }) => {
    // 只做起点准备：登录态 + 打开页面。不在这里加购、不下单。
    await page.goto('/cart');
    cartPage = new CartPage(page);
    await cartPage.ready();
  });

  test('空购物车显示提示', async () => {
    await expect(cartPage.emptyHint).toBeVisible();
  });
});
```

**隔离的硬判据**：把 `test.describe` 里的用例**倒序**跑一遍，结果必须完全相同。有任何一条变红或变绿，就存在状态泄漏——往往来自「上一条用例留下的登录态/购物车内容/未清理的 mock 路由」。

登录态优先走 `storageState` 注入（`use: { storageState: '.playwright-artifacts/state/u1.json' }`），不要每条用例都真的走一遍登录 UI：那既慢，又让「登录页坏了」把几十条无关用例一起染红，掩盖真正的失败。状态文件同样落盘到 `.playwright-artifacts/state/`。

## 3. 容器与用例分开处理

`describe` 和 `test.step` 是**容器**，不是用例。它们的作用是分组和分层报告，本身不承载断言。

```ts
test.describe('结算页', () => {           // 容器：只分组，不该被要求有断言
  test('金额为 ¥99.00', async ({ page }) => {
    await test.step('填写收货信息', async () => {   // 容器：只分层，不该被要求有断言
      await page.getByLabel('收货人').fill('张三');
    });
    await expect(page.getByTestId('order-amount')).toHaveText('¥99.00');  // 断言在这里
  });
});
```

**为什么 `describe` / `test.step` 不参与断言检查**：容器当然没有断言——它的职责就是分组。如果 PW007 不排除容器，一个文件里每个 `describe` 和每个 `step` 都会被判成「用例内没有断言」，一次冤枉十几处。而在门禁这件事上，**一次冤枉就够把公信力废掉**：团队会认为规则不可信，然后整体关掉它，连真正的假通过一起放过。

同理，`test.step` 的正确用法是让失败报告能显示「走到了哪一步」，而不是把断言藏进 step 里让报告读起来更整齐。断言写在 step 内是允许的（它属于外层用例），但要保证外层用例整体能看到它。

## 4. `test.only` 泄漏（PW002）与 `forbidOnly` 双保险

- **判据**：文件里出现 `test.only(` 或 `describe.only(`。命中即 ERROR，阻断提交。
- **反例**：

```ts
// ✗ PW002：本地调试完忘了删。CI 上整条流水线只跑这一条，却报绿。
test.only('下单金额正确', async ({ page }) => { /* ... */ });
describe.only('购物车', () => { /* ... */ });
```

- **正确做法**：提交前删光 `.only`；同时在配置里开 `forbidOnly` 做双保险。

```ts
// playwright.config.ts
export default defineConfig({
  forbidOnly: !!process.env.CI,   // CI 上遇到 .only 直接失败（`check_config` CFG001）
});
```

- **评审检查点**：`grep -n "\.only(" tests/` 必须为空；同时确认 `playwright.config.ts` 里 `forbidOnly` 没有被显式写成 `false`（`check_config` 会把这判成 ERROR CFG001）。
- **为什么必须双保险**：`lint_spec` 是静态扫描，它只看你交给它的文件。如果 `.only` 出现在没被扫描到的目录、或扫描发生在提交之后，静态规则就漏了。`forbidOnly` 是运行时的最后一道闸：它在 CI 上让 `.only` **直接失败**，而不是悄悄缩小测试范围。`forbidOnly: false` 等于放弃这道保险。
- **为什么这条值得单独设一条规则**：`.only` 泄漏的后果不是「少跑一些用例」那么轻——它让整条流水线**报绿**。绿色的假报告比红色的真失败贵得多：它让你以为验证过了。
- 一个已知的坑（工具实现层面，评审时也值得知道）：块起始正则不能写成 `test\s*\(`，否则 `test.only(` 的用例体根本扫不到——**用来拦 `.only` 的规则会被 `.only` 自己骗过去**。所以正则必须允许 `test` 与 `(` 之间存在 `.word`。

## 5. PW103｜静默的 `test.skip` / `test.fixme`（WARN，人工确认）

- **判据**：出现 `test.skip(` 或 `test.fixme(`。报 WARN。
- **反例**：

```ts
// ✗ PW103：跳过没有任何理由，也没人知道什么时候能恢复
test.skip('退款流程', async ({ page }) => { /* ... */ });

// ✓ 带理由和跟踪单号
test.fixme(true, 'ISSUE-123 等待退款接口修复后恢复');
test.skip(true, 'ISSUE-456 该场景已下线，等产品确认删除');
```

- **评审检查点**：这条用例为什么被跳过？如果答不出单号，它就已经变成了**永久的盲区**。跳过的用例不会失败、不会报警、不会进任何 dashboard——它会静默积累，直到某天有人发现「我们有一半场景其实从没跑过」。
- **为什么是 WARN 而不是 ERROR**：跳过有时是合法且负责的动作（场景下线、依赖未就绪）。规则能判定的是「有没有写理由和单号」，不能判定「理由是否成立」。所以它报出来交人确认，不阻断。
- 配套的纪律：跳过的理由必须指向一个可追踪的工单，且该工单的关闭条件是「恢复这条用例」或「删除这条用例」——不允许「挂着不管」。

## 6. PW104｜`test.slow()` 放宽超时（WARN，人工确认）

- **判据**：出现 `.slow()`。报 WARN。
- **反例**：

```ts
// ✗ PW104：把超时乘三来「解决」慢，是掩盖而不是修复
test.slow();
test('导出全部订单报表', async ({ page }) => { /* ... */ });
```

```ts
// ✓ 确属正常长流程：注释写明预期耗时与上限
test.slow(); // 该场景需全量生成 10 万行报表，正常耗时 60–90s（见 ISSUE-789 实测记录）
test('导出全部订单报表', async ({ page }) => { /* ... */ });
```

- **评审检查点**：这条用例原本为什么超时？如果原因是「页面/接口变慢了」，`test.slow()` 与放宽超时**同罪**——它把「功能坏了」拖延成「跑得很慢」，只是把红色推迟了几十秒。如果原因是「这个场景本来就长」（批量导出、报表生成），写明实测耗时区间与上限即可放行。
- **为什么是 WARN**：静态扫描无法区分「正常长流程」与「掩盖慢」。但它必须被看见，因为放宽超时会让这条用例的失败永远呈现为 `timeout` 类归因，看不出真正的破点。

## 7. PW102｜提交前遗留的调试代码（ERROR，阻断）

- **判据**：出现 `debugger;` 或 `page.pause(`。命中即 ERROR。
- **反例**：

```ts
// ✗ PW102：CI 上会一直挂到超时，把一条真实失败伪装成「超时」
debugger;
await page.pause();
```

- **评审检查点**：`page.pause()` 与 `debugger` 会让 CI 挂住直到超时。这类提交的典型症状是「本地跑得好好的，CI 上全红且都是超时」——排查成本极高，因为它看起来像环境问题。
- **为什么这么定**：这是唯一一条「作者的调试习惯会直接污染 CI 结论」的规则。它完全可以在提交前机械地拦住，没有讨论空间。
