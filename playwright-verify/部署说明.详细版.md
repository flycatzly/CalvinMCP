> **v1.8.15** · 14 个 MCP 工具 + 1 个 Skill · 13 套件 686 断言（含真实浏览器矩阵）· 版本记录见 README「版本记录」
> 目标读者：要把它装到本机、团队机器或 CI 上的工程师。本文是完整参考；最短路径见同目录 [部署说明.md](./部署说明.md)。

  解压 / 拷贝即可部署。零 npm 依赖，不需要 `npm install`、不需要联网、不需要生成任何依赖。

## 1. 环境要求

| 组件 | 要求 | 缺失后果 |
|---|---|---|
| **Node.js** | ≥ 18.17（实测 v24.15） | 无法启动（必需项） |
| Python | ≥ 3.9（`openpyxl` 可选） | 只有 `orchestrate_excel` 的 `.xlsx` 读取受影响；`.csv` 与其余全部工具正常。`.xlsx` 缺 `openpyxl` 时自动用内置 zip+XML 解析兜底，不再整条失效 |
| `@playwright/test`（可选） | 1.63+ | 只有 `run_verify` 与真实回归不可用；扫描/体检/归因/生成/智能体规划全部正常 |
| `@playwright/cli`（可选） | 0.1.22+ | `cli_health` / `cli_session` 与智能体线执行层（`nl_test_goal` 真执行、`explore_page`）不可用 |
| 浏览器 | Chromium / Chrome / Edge 任一 | `cli_*` 与真实回归需要；缺浏览器时失败归成 `env` 归因并给出修法（`npx playwright install chromium`） |

**关键设计：可选依赖缺失只影响对应工具，不会让服务起不来。**
`selfcheck` 会明确区分「必需项」与「可选项」，缺失项逐条说明缺什么。

上表除 Node.js 外全是**可选项**（执行层需要，且由被测项目 / 本机自己提供）——
本包零 npm 依赖，**部署本工具不需要安装任何依赖**，解压 / 拷贝即可部署。

> DSH 用户注意：运行时的 Python 自带 `openpyxl`，`resolvePython()` 会自动找到它
> （`~/.dsh/dsh-runtimes/dsh-primary-runtime/dependencies/python/python.exe`），无需额外安装。

## 2. 快速部署（推荐路径）

```powershell
cd <项目根>            # 例如 D:\Users\DeepSeekWeb\playwright-verify-mcp（或拷贝解压后的任意目录）

# ① 一键安装：环境检查 + 装 Skill + 生成 DSH bundle + 注册 MCP 客户端
#    --target 指定默认工作目录（会写进 MCP 注册项的 PVMCP_CWD，省得每次调用都传 cwd）
node skill\playwright-verify\install.mjs --target "D:\path\to\your-project"

# ② 自检
node skill\playwright-verify\scripts\selfcheck.mjs

# ③ 重启 MCP 客户端 / 重新加载 DSH 配置
```

> 本包零 npm 依赖 —— 部署**不需要** `npm install` / `npm ci`，不需要联网。
> 执行层可选依赖（要用 `run_verify` / `cli_*` / 智能体线执行层才需要）由使用方自己提供：
> 被测项目里 `npm i -D @playwright/test`（`run_verify` 刻意用被测项目自己的版本）；
> `npm i -g @playwright/cli@latest` + `playwright-cli install`（CLI 类与智能体线执行层）；
> 浏览器用本机已有的 Edge / Chrome / Chromium 即可。

安装器做四件事，每件都可单独跳过：

| 步骤 | 内容 | 跳过参数 |
|---|---|---|
| 1 | 环境自检（Node 版本、可选依赖） | — |
| 2 | 装 Skill 到 `~/.agents/skills/` | `--skills-only` 只做这步 |
| 3 | 生成 DSH MCP bundle（manifest + cordis.patch.yml） | `--skills-only` |
| 4 | 注册到 Claude Code / Desktop / Cursor（改前自动备份） | `--no-register` |

常用参数：

| 参数 | 作用 |
|---|---|
| `--target <目录>` | 默认工作目录，写进注册项的 `PVMCP_CWD`（**建议显式指定你的项目根**） |
| `--force` | 重建安装目录（只删 `mcp/`、`skill/`、`demo/` 三个子树，不动别的） |
| `--print-config` | 只打印配置片段，不写任何文件 |
| `--no-register` | 不动客户端配置 |
| `--skills-only` | 只装 Skill |
| `--uninstall` | 只移除客户端注册项 |

**先看后做**（不写任何文件，只打印配置片段）：

```powershell
node skill\playwright-verify\install.mjs --print-config
```

成功标志：

```
INSTALL_STATUS=OK
```

失败时输出 `INSTALL_STATUS=FAIL FAILED=<n>` 并逐条列出失败项。

## 3. 手动部署

不想用安装器时，手工三步：

### 3.1 装 Skill

```powershell
$src = "<项目根>\skill\playwright-verify"
$dst = "$env:USERPROFILE\.agents\skills\playwright-verify"
New-Item -ItemType Directory -Force -Path $dst | Out-Null
Copy-Item -Recurse -Force "$src\*" $dst
```

确认 `~/.agents/skills/playwright-verify/SKILL.md` 存在 —— **路径必须是这个形状**，
否则 agent 不会自动匹配，任务又会走回「手写命令」的老路。重启 agent 后在 Skill 列表里确认它加载了。

### 3.2 让脚本能找到核心库

`scripts/` 里的命令会按以下顺序找 `mcp/lib`：

1. `$PVMCP_LIB`
2. `$PVMCP_HOME/mcp/lib`
3. 从脚本位置向上逐级找 `mcp/lib`（仓库布局）
4. `~/.agents/skills/playwright-verify-mcp/mcp/lib`（全局安装布局）

推荐做法：把整个项目复制到 `~/.agents/skills/playwright-verify-mcp/`（保持 `mcp/` 与 `skill/` 并列），
这样第 4 条就能命中。或者直接设环境变量：

```powershell
# 用户级持久化
[Environment]::SetEnvironmentVariable('PVMCP_HOME', '<项目根>', 'User')
```

### 3.3 注册 MCP server

见下面第 4、5 节。最简形式：

```json
{
  "mcpServers": {
    "playwright-verify": {
      "command": "node",
      "args": ["<绝对路径>/mcp/server.mjs"]
    }
  }
}
```

> **必须用绝对路径**。`mcp/server.mjs` 用 `import.meta.url` 定位同目录的 `lib/` 与 `package.json`，
> 所以它是位置无关的，但客户端的 cwd 通常不是项目根，相对路径会找不到文件。

## 4. DSH 部署（官方 mcp-client 插件方式）

DSH 不是读一个 JSON 文件，而是把 MCP server 当作**插件**插入 Cordis 组合。
官方包是 `@deepseek-ai/dsh-mcp-client`，工具会以 `mcp__<serverName>__<tool>` 出现。

### 4.1 用安装器生成的 bundle（推荐）

`install.mjs` 会在 `~/.agents/skills/playwright-verify-mcp/dsh-bundle/` 生成两个文件：

**`package.json`** —— 配置型 bundle 的 manifest：需要有唯一 name、version 和 `dsh.bundle.patch`，
但**不需要** Host / Client 入口文件。

```json
{
  "name": "@local/playwright-verify-mcp",
  "version": "1.0.0",
  "private": true,
  "type": "module",
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}
```

**`cordis.patch.yml`** —— 插入已经安装好的 mcp-client 插件：

```yaml
- insert:
    - id: playwright-verify-mcp
      name: '@deepseek-ai/dsh-mcp-client'
      config:
        serverName: playwright_verify
        transport: stdio
        command: "D:\\Users\\node-v24.15.0-win-x64\\node.exe"
        args:
          - "C:\\Users\\CalvinZly\\.agents\\skills\\playwright-verify-mcp\\mcp\\server.mjs"
        cwd: "C:\\Users\\CalvinZly\\.agents\\skills\\playwright-verify-mcp"
        toolCallTimeoutMs: 600000
        failOnStartupError: true
```

然后把该 bundle 目录安装进 DSH（`plugin_manager`），或把这几个 `insert` 条目合并进你的 profile 组合。

### 4.2 mcp-client 配置字段速查

| 字段 | 默认 | 含义 |
|---|---|---|
| `transport` | 必填 | `stdio` 或 `streamable-http` |
| `serverName` | 必填 | 工具名命名空间，`[A-Za-z0-9_-]{1,32}`，同一注册作用域内唯一 |
| `command` / `args` / `env` / `cwd` | — | stdio：可执行文件、参数、额外环境变量、工作目录 |
| `toolCallTimeoutMs` | 60000 | 每次 `tools/call` 的超时 |
| `maxInstructionBytes` | 32768 | 服务端 instructions 的 UTF-8 字节上限，超限会拒绝连接 |
| `failOnStartupError` | false | 首次连接或工具同步失败时是否让插件激活失败 |
| `reconnect.enabled` | true | 断线自动重连 |
| `reconnect.initialDelayMs` / `maxDelayMs` / `maxAttempts` | 500 / 30000 / 10 | 重连退避参数 |

**两个要点：**

- **`toolCallTimeoutMs` 建议调到 600000（10 分钟）。** 默认 60 秒对 `run_verify`
  与 `orchestrate_excel` 这类长任务明显不够 —— 它们真的会跑几分钟的回归。
- **`failOnStartupError: true` 的取舍**：连不上就让插件激活失败，你立刻知道；
  设 false 则服务照常启动，但静默少一批工具 —— 那种「以为装了其实没装」最难查。
  本工具默认给 `true`。

### 4.3 验证

重启 DSH 后，工具应出现在模型工具列表里，名字是 `mcp__playwright_verify__<tool>`：

```
mcp__playwright_verify__check_config
mcp__playwright_verify__lint_spec
mcp__playwright_verify__summarize_report
mcp__playwright_verify__run_verify
mcp__playwright_verify__cli_health
mcp__playwright_verify__cli_session
mcp__playwright_verify__generate_scripts
mcp__playwright_verify__check_standards
mcp__playwright_verify__orchestrate_excel
mcp__playwright_verify__explain_rules
mcp__playwright_verify__selfcheck
mcp__playwright_verify__explore_page
mcp__playwright_verify__nl_test_goal
```

让模型调用 `mcp__playwright_verify__selfcheck`。看到必需项全 PASS 就算接好了。

> **注意 stdio 的行为**：客户端在协商阶段会起一个**临时探测进程**，然后才起服务进程。
> 所以看到两个 node 进程是正常的。

## 6. 安装产物布局

`install.mjs` 之后的目录形状：

```
~/.agents/skills/
├── playwright-verify/                     ← Skill（agent 按 SKILL.md 发现它）
│   ├── SKILL.md
│   ├── references/    12 篇知识层文档
│   ├── scripts/       8 个命令行包装
│   ├── assets/        5 个模板
│   └── install.mjs
└── playwright-verify-mcp/                 ← 项目副本（MCP server + 同一份核心库）
    ├── mcp/
    │   ├── server.mjs                     ← MCP 入口
    │   ├── lib/                           ← 核心逻辑（唯一判定真相源）
    │   ├── py/read_cases.py               ← Excel 读取助手
    │   └── test/                          ← 13 套回归测试
    ├── skill/playwright-verify/           ← 同一份 Skill
    ├── demo/                              ← 样例集与可离线复现的演示回归
    ├── node_modules/                      ← 可选依赖（要用执行层才装；纯净发布包不含它）
    ├── .playwright/cli.config.json        ← CLI 浏览器通道（install.mjs 按目标机器生成）
    └── dsh-bundle/                        ← DSH 插件 bundle
        ├── package.json
        └── cordis.patch.yml
```

> 纯净发布包本身**不含任何 `.` 前缀内容**：上图的 `.playwright/` 是装机时按目标机器
> 生成的，`dsh-bundle/` 是 `install.mjs` 生成的，`node_modules/` 需要执行层才装 ——
> 解压 / 拷贝出来的目录可以直接跑 `install.mjs`。

**为什么 `scripts/` 与 MCP 跑同一份 `mcp/lib`**：两边结论必须一致。
如果 MCP 说 ERROR 0、脚本说 ERROR 2，门禁的公信力一次性就废了。

## 7. 验证部署

### 7.1 服务自检

```
selfcheck { cwd: "<项目根>" }
```

或命令行：

```bash
node skill/playwright-verify/scripts/selfcheck.mjs
```

期望输出：

```
PASS 核心库（mcp/lib）: <路径>
PASS 等长脱敏不变量: 7 组样例通过
PASS lint 规则表: 20 条（ERROR 10 / WARN 10）
PASS Playwright 运行器: node @playwright/test/cli.js      ← 可选项
PASS playwright-cli: node @playwright/cli/playwright-cli.js ← 可选项
PASS Python（Excel 编排）: <python 路径>                    ← 可选项
PASS references 知识层: 12 篇
PASS assets 资产层: 5 个模板

必需项全部通过。
```

### 7.2 全量回归（部署后强烈建议跑一次）

```bash
# 不含浏览器（快，验证核心判定逻辑）
node mcp/test/verify-all.mjs

# 含真实浏览器回归（约 30 秒，验证执行层与聚类在真数据上成立）
node mcp/test/verify-all.mjs --with-browser
```

期望：

```
结果：13/13 套全部通过 ✅
```

`--with-browser` 会核对示例矩阵：**2 通过 / 6 失败 / 1 偶发 → 聚成 4 个根因签名**
（`assertion:3 locator-strict:1 timeout:1 env:1`）。这个矩阵是刻意铺开的，用来证明聚类真的可用。
不带 `--with-browser`（或缺可选依赖）时浏览器相关的 4 套自动 SKIP，其余 8 套照常出结论。

收尾约定：**全部通过后自动清理本次运行的产物目录**（`.playwright-artifacts/`、`.playwright-cli/`、
`test-results/`、`demo/generated*` 等，见 §15.1 为什么会产出这些目录）；**失败时全部保留**当现场；
想留证据加 `--keep-artifacts`（`node mcp/test/verify-all.mjs --with-browser --keep-artifacts`）。

### 7.3 端到端冒烟

```bash
S=skill/playwright-verify/scripts

# 基线配置必须 PASS
node $S/check_config.mjs demo/configs/playwright.config.baseline.ts

# 反例配置必须 BLOCK（退出码 1）
node $S/check_config.mjs demo/configs/playwright.config.legacy.ts ; echo "exit=$?"

# 三份样例集：clean 不报、messy 全中、tricky 不误报
node $S/lint_spec.mjs demo/tests/clean.spec.ts
node $S/lint_spec.mjs demo/tests/messy.spec.ts

```

## 8. CI 集成

仓库已自带 `.github/workflows/ci.yml`，三个作业分工如下。

### 8.1 作业结构

| 作业 | 平台 | 目的 |
|---|---|---|
| `gate` | ubuntu | **门禁线示范**：配置体检 → 用例扫描，并断言「坏样例必须返回退出码 1」 |
| `verify` | ubuntu × node 20/22 | 全量回归（13 套，含真实浏览器）+ 归档证据 |
| `portable` | windows | **跨平台一致性**：换行符/路径分隔符/子进程 shim 这些问题只在跨平台时暴露 |

### 8.2 为什么 CI 不另写一套命令

CI 跑的就是本地那条命令（`npm run test:full`）。另写一套很容易变成
「CI 绿、本地红」或反过来 —— **那等于两套事实**。

### 8.3 `gate` 作业在验证「门禁真的有阻断力」

只跑一遍样例是不够的。CI 里显式断言退出码：

```bash
set +e
node skill/playwright-verify/scripts/lint_spec.mjs demo/tests/messy.spec.ts
code=$?
set -e
if [ "$code" -ne 1 ]; then
  echo "::error::含 ERROR 的用例应返回退出码 1，实际为 $code"
  exit 1
fi
```

理由：**只有 WARN 的检查等于没有检查**。门禁一旦不能阻断，就等于没有门禁 ——
这条断言防的正是有人把门禁改成「跑一遍就算过」。

`mcp/py/validate_ci.py` 还会静态校验工作流自身结构（含「gate 作业是否真的在校验退出码」），
可以用 `python mcp/py/validate_ci.py` 单独跑。

### 8.4 可复现的本地等价命令

```bash
npm ci                                              # 与实际 CI 一致（只为跑浏览器矩阵装可选依赖，部署不需要）
npx playwright install --with-deps chromium          # 只有 verify 作业需要
node skill/playwright-verify/scripts/setup-cli-config.mjs --channel chromium  # CI 没有 Edge
npm run test:full                                    # = node mcp/test/verify-all.mjs --with-browser
```

在 Windows 本机跑同一套（`setup-cli-config.mjs` 会自动选 msedge）：

```powershell
npm ci                   # 同上：只为可选依赖（本包零 npm 依赖，部署不需要这步）
npx playwright install chromium
node skill\playwright-verify\scripts\setup-cli-config.mjs
npm run test:full
```

### 8.5 用在你自己的项目上

`ci.yml` 验证的是**本工具自己**。要把三条门禁用到你的项目，最小片段：

```yaml
name: playwright-gate
on: [push, pull_request]
jobs:
  verify:
    runs-on: ubuntu-latest
    env:
      CI: "true"                 # 触发 forbidOnly / retries / workers 的 CI 分支
      BASE_URL: ${{ vars.TEST_BASE_URL }}
      PW_U1_USERNAME: ${{ secrets.PW_U1_USERNAME }}
      PW_U1_PASSWORD: ${{ secrets.PW_U1_PASSWORD }}
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: '20', cache: npm }

      # 被测项目自己的测试依赖 —— 本工具零 npm 依赖、拷贝即用，这里不需要装它
      - run: npm ci
      - run: npx playwright install --with-deps chromium

      # ① 配置体检：放最前面，因为它错的时候后面全是白干
      - name: 配置体检
        run: node node_modules/playwright-verify-mcp/skill/playwright-verify/scripts/check_config.mjs playwright.config.ts

      # ② 用例静态门禁：ERROR 必须为 0
      - name: 用例静态门禁
        run: node node_modules/playwright-verify-mcp/skill/playwright-verify/scripts/lint_spec.mjs tests/

      # ③ 回归（不阻断，先把证据与归因拿到手）
      - name: 回归
        id: run
        continue-on-error: true
        run: node node_modules/playwright-verify-mcp/skill/playwright-verify/scripts/run_verify.mjs --cwd . --config playwright.config.ts

      # ④ 失败归因：无论成败都跑，产物直接当工单附件
      - name: 失败归因
        if: always()
        run: node node_modules/playwright-verify-mcp/skill/playwright-verify/scripts/summarize_report.mjs test-results/report.json

      - name: 归档证据
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: playwright-evidence
          path: |
            .playwright-artifacts/
            test-results/

      - name: 按回归结果判定
        if: steps.run.outcome == 'failure'
        run: exit 1
```

**三个脚本的顺序不能换**：配置体检最前（它错的时候后面全是白干）→ 用例扫描挂合入前 →
报告聚类挂失败任务里（`if: always()`，否则失败时归因不跑，等于白跑一趟）。

> 路径说明：上面写的是 `node_modules/playwright-verify-mcp/...`（把本工具作为依赖安装时的形态）。
> 若用 Skill 方式装到 `~/.agents/skills/`，改成对应绝对路径或设 `PVMCP_HOME`。

### 9.1 MCP server

| 变量 | 默认 | 说明 |
|---|---|---|
| `PVMCP_CWD` | `process.cwd()` | **建议设成你的项目根**。设了它，模型调用工具时不必每次传 `cwd`（多轮对话里省 token，也避免忘传就去扫错目录）。安装器会把它写进生成的注册项 |
| `PVMCP_LOG` | 未设置 | 设了就写协议日志：每请求一行结构化观测记录（`name/ms/outcome/code`，nl_test_goal 另带可选 `cache=hit\|miss\|skip`，可离线聚合调用量/成功率/延迟分布/错误分布/计划缓存命中率），排查握手问题也用它。未设置时不写任何日志 |
| `PVMCP_LOG_MAX_MB` | `2` | 日志容量上限（MB）：超过就轮转 —— 当前文件改名 `<file>.1`、新日志从轮转标记行起（`log_summary` 会提示轮转前件，调用量少一段不再静默）。`0`=关闭轮转（外挂轮转方案的留口）；非法值回退默认 2MB 并向 stderr 提示一次 |
| `PVMCP_NO_LISTEN` | 未设置 | `=1` 时不启动 stdio 循环（自检用） |
| `PVMCP_FORCE_LISTEN` | 未设置 | `=1` 时强制启动 stdio 循环。用于宿主用包装器/`--eval` 改变 `argv` 的场景（正常情况下服务按真实路径判断自己是不是入口，改名与软链都不受影响） |

### 9.2 Skill 脚本

| `PVMCP_LIB` | 未设置 | 直接指向 `mcp/lib` 目录（优先级最高） |
| `DSH_PYTHON` | 未设置 | 指定 Python 解释器路径（Excel 编排用） |

### 9.4 CLI 浏览器通道

文件：`.playwright/cli.config.json`（Playwright 从 cwd 读取）

**不要手工写死通道** —— 它是跨平台最容易踩的坑。`install.mjs` 安装时会自动按
目标机器适配这份配置（配置声明的平台与当前平台不符时重新生成；手工写的配置原样保留；
`PVMCP_BROWSER_CHANNEL` 环境变量显式指定时按它生成），所以「装完忘生成」这类问题
不会再出现。需要手动调整时用脚本按平台生成：

```bash
node skill/playwright-verify/scripts/setup-cli-config.mjs            # 按平台自动选
node skill/playwright-verify/scripts/setup-cli-config.mjs --channel chromium   # 显式指定
node skill/playwright-verify/scripts/setup-cli-config.mjs --print    # 只看不写
```

选择规则：

| 环境 | 通道 | 原因 |
|---|---|---|
| Windows（默认） | `msedge` | 系统自带 Edge，省一次浏览器下载 |
| Linux / macOS（默认） | 不指定（用 chromium） | 这些平台没有 Edge |
| `PVMCP_BROWSER_CHANNEL` 环境变量 | 用它 | 团队统一指定 |
| `--channel` 参数 | 用它 | 单次覆盖，优先级最高 |

**两条实测教训**（都表现为「看起来像环境问题」）：

1. **不写通道**：源码目录与安装目录会落到**不同的默认通道**
   （实测源码用 msedge、装完去找 chrome），于是「这里能跑、装完就不能跑」。
2. **写死 msedge**：Windows 上稳了，但 **Linux/CI 上没有 Edge**，
   `cli_health` 会以 `Chromium distribution 'msedge' is not found` 失败。

所以 CI 里必须显式指定 chromium（见 `ci.yml` 的 `setup-cli-config.mjs --channel chromium` 步骤）。

### 9.5 换行符（跨平台一致性的前提）

仓库根有 `.gitattributes`，声明 `* text=auto eol=lf`。**这不是洁癖**：

- `mcp/py/read_cases.py` 带 shebang，CRLF 会让 Linux 上的 `#!/usr/bin/env python\r` 找不到解释器；
- 生成的 `.ts/.mjs` 要过语法门禁与 Playwright 解析，换行符不同会让
  `deployed-check` 的全树哈希比对在不同平台上**无故报漂移**（假失败）；
- Markdown/JSON 会因整文件 diff 淹没真正的改动。

> 验证方式：`mcp/test/hardened-check.mjs` 的 H10 直接读字节断言 LF，不依赖 git 命令。

### 9.6 LLM（智能体线 `nl_test_goal`）

LLM 只做规划（目标 → 受限计划），执行与判定走确定性链路，所以 **LLM 是可选项**：
配了多一个入口，没配就走降级骨架（`fallbackPlan`），工具照常可用。

| 变量 | 默认 | 说明 |
|---|---|---|
| `PVMCP_LLM` | `ollama` | `ollama`（本地）/ `deepseek`（云端，**显式开启**）/ `off`（不用 LLM，走降级骨架） |
| `OLLAMA_BASE_URL` | `http://127.0.0.1:11434` | 本地 Ollama 服务地址（数据不出机） |
| `OLLAMA_MODEL` | `qwen3` | 本地模型名（需支持 JSON 输出） |
| `DEEPSEEK_API_KEY` | 未设置 | **只从环境变量读**，不进参数/磁盘/日志（全程掩码）。未设置时 `deepseek` 明确报 `LLM_KEY_MISSING`，不静默回落 |
| `DEEPSEEK_BASE_URL` | 官方地址 | 兼容网关可覆盖 |
| `DEEPSEEK_MODEL` | `deepseek-chat` | 云端模型名 |
| `PVMCP_LLM_TIMEOUT_MS` | 20000 | 单次规划请求超时（毫秒） |

三条边界（部署时需要知道的）：

1. **默认本地**：`PVMCP_LLM` 缺省走 Ollama，页面目标文本不出机；云端必须显式开。
2. **截图与页面快照永不进 LLM 请求** —— 送给模型的只有目标文本与步骤清单。
3. **危险目标在调 LLM 之前就拒绝**（真实资金/破坏性数据/生产/对外发送/批量对外），
   LLM 配没配都不影响守门。

自检：MCP 的 `selfcheck` 工具会多出一行「LLM（智能体线）」可选项报告（缺配置只提示，不阻断；
实测输出形如 `PASS LLM（智能体线）: ollama/qwen3：Ollama 本地（数据不出机）`）。

## 12. 故障排查

### 12.1 客户端里看不到工具

| 检查 | 做法 |
|---|---|
| 服务能独立起来吗 | `node mcp/server.mjs` 后手动发一行 `{"jsonrpc":"2.0","id":1,"method":"tools/list"}`，应回 JSON |
| 路径是绝对路径吗 | 客户端 cwd 通常不是项目根，相对路径必然失败 |
| 重启过客户端吗 | 配置变更需要重启或重新加载 |
| Skill 路径对吗 | 必须恰好是 `~/.agents/skills/playwright-verify/SKILL.md` |
| DSH 的 `failOnStartupError` | 设为 `true` 时启动失败会明确报错；看日志确认原因 |

### 12.2 打开协议日志

```powershell
$env:PVMCP_LOG = "$env:TEMP\pvmcp.log"
node mcp\server.mjs
```

日志会记录 initialize（含客户端名与版本协商结果）、每次 `tools/call` 的名称与耗时、异常堆栈。

### 12.3 `cli_health` 失败

报错会直接翻译成人话：

```
诊断：本机缺少 CLI 需要的浏览器 —— Chromium distribution 'chrome' is not found at ...
两条修法（任选）：
  1) 装它：npx playwright install chrome
  2) 或改用本机已有的浏览器通道：编辑 .playwright/cli.config.json ...
```

### 12.4 `run_verify` 说找不到 Playwright

```
<项目> 下找不到 Playwright。请先在该项目执行：
  npm i -D @playwright/test && npx playwright install chromium
```

注意 `run_verify` 找的是**目标项目**里的 Playwright（`node_modules/@playwright/test/cli.js`），
不是本工具自己的。这是刻意的：用被测项目自己的版本跑，避免版本错配。

### 12.5 `orchestrate_excel` 说找不到 Python

```
找不到 Python，无法解析 Excel。请装 Python（≥3.9，xlsx 读取有内置解析，
不需要第三方库），或把用例表另存为 .csv —— csv 可以用纯 Node 读取。
```

装了 DSH 运行时的环境自带 Python + openpyxl，`resolvePython()` 会自动找到。
也可以用 `DSH_PYTHON` 显式指定。
普通 Python 3.9+ 即可：`.xlsx` 缺 `openpyxl` 时自动回落到内置 zip+XML 解析
（用例表场景全覆盖：共享字符串、行内字符串、布尔、数值、公式缓存值；
日期序列号不转换，装有 `openpyxl` 时不受影响）。

### 12.6 Excel 表头没被识别

`read_cases.py` 在前 10 行里找「命中别名最多」的那一行作为表头，至少需要认出 2 列。
支持的别名：

| 列 | 认得的写法 |
|---|---|
| 用例 | 用例 / 用例名称 / 用例标题 / 场景 / case / title / name |
| 步骤 | 步骤 / 操作步骤 / 测试步骤 / 执行步骤 / steps / step |
| 预期 | 预期 / 预期结果 / 期望结果 / 验收点 / 断言 / expect |
| 环境 | 环境 / env / environment |
| 账号 | 账号 / 账户 / 用户 / account / user |

仍然认不出时，会明确报「没能识别出表头行」并列出要求，不会瞎猜。

### 12.7 工具调用超时

默认 `toolCallTimeoutMs` 是 60 秒，对长回归不够。改成：

```yaml
toolCallTimeoutMs: 600000
```

### 12.8 日志里出现「The 'NO_COLOR' env is ignored」警告

这是 Playwright 的 worker 启动时硬编码 `FORCE_COLOR=1` 与我们设的 `NO_COLOR` 冲突，
Node 自己打的警告，**不是被测对象的错误**，不影响归因与判定。
它对人有害的只有一面：刷屏 stderr，把真正的失败原因挤出「只看尾部几行」的诊断窗口 ——
所以工具的摘要/尾部输出已自动剔除这些行（`stripKnownNoise`），落盘日志保持原样供归档。

### 12.9 端口 / 进程类问题

stdio 传输不占端口。如果看到残留进程：

```powershell
npx playwright-cli close-all
npx playwright-cli kill-all
```

## 13. 安全说明

### 13.1 凭据

- **绝不写死在脚本、Skill、生成的用例里。** `lint_spec` 的 PW101 会把这个判成 ERROR。
- 只从环境变量读（`process.env.PW_*`），或走密钥管理。
- 缺环境变量时**明确失败**，不要回退到默认密码 —— 那会在错误的账号上跑出「通过」。
- DSH 的 mcp-client 会清洗环境变量（scrubbed ambient env），要用环境变量请用 Loader 的 `!!js` 引用，
  不要把密钥复制进对话文本。

### 13.2 环境隔离

- **默认只允许 test / staging。** 生产验证必须走独立审批。
- `lint_spec` 的 PW107 会拦用例里出现的生产域名。
- `check_config` 的 CFG012 会检查是否有环境开关。
- 建议在 CI 上显式拒绝 `BASE_URL` 命中 `prod` / `production`：

```bash
case "$BASE_URL" in *prod*) echo "拒绝在生产环境跑自动化"; exit 1;; esac
```

### 13.3 不可自动化执行的边界

涉及**真实支付、真实用户数据**的操作一律不可自动化执行。这条写在 SKILL.md 的硬规则里。
`generate_scripts` 也不接受把生产域名当导航目标。

### 13.4 不自动改断言

「把断言放宽到能过」和「修好定位器」在代码上长得几乎一样。工具只产出提案与门禁结论，
**判断必须由人来做**。所以 `run_verify` 不会自动修复，`summarize_report` 对 `assertion` 类的结论是「待定」。

### 13.5 文件访问面

- 读：目标项目里的用例与配置、报告文件。
- 写：只写安装目录、`.playwright-artifacts/`、以及 `generate_scripts` 显式指定的 `outDir`。
- **门禁不过就不写盘**（语法或 lint ERROR 任一不过都阻止）。
- 安装器改客户端配置前会备份成 `<文件>.bak-playwright-verify`。

### 13.6 网络

服务本身不联网。网络访问只发生在被测项目的浏览器操作里（由 `cli_*` / `run_verify` 驱动）。
`cli_session` 只允许在白名单内的子命令，不接受任意命令透传。

### 14.2 全工具逐条示例（14/14 覆盖）

每个工具给「怎么说 → 会发生什么」。同一意图说法不唯一，意思到了即可。

**1) `check_config` —— 配置基线体检（放流水线最前面）**

> 你说：「帮我检查一下 playwright.config.ts 可不可信」/「配置体检做一下」
>
> 会发生：逐条过 CFG001–CFG012（forbidOnly / 超时 / trace / json reporter…），ERROR → isError 且退出码 1。
> 红线：判据不明时降级 INFO 交人确认，绝不因为算不出来就误报。

**2) `lint_spec` —— 用例静态扫描（20 条规则）**

> 你说：「tests/ 目录过一遍规则，能不能合入」/「扫一下 checkout.spec.ts 有什么坏味道」
>
> 会发生：ERROR 必须为 0 才放行；每条命中都带**回原文的证据行**。可以说「只跑核心 14 条」「把 PW011 提级成 ERROR」。
> 红线：不许因为「改起来麻烦」就关规则——关掉的是保护，不是告警。

**3) `summarize_report` —— 失败聚类归因（单报告 / 多报告趋势）**

> 你说：「CI 上 6 条失败，帮我看看该谁修」；趋势：「和上周比有没有回退」→ 传 `files`（N 份报告或目录）
>
> 会发生：失败压成根因签名 + 五类归因 + 派活口径；趋势给通过率曲线与签名漂移（新签名=回归信号/消除=修复成效/持续=存量），
> 趋势 md/JSON 落盘、structuredContent 有界（每列表截 50 + total 诚实）。`assertion` 类结论是「待定」——必须人判。
> 红线：断言绝不自动放宽；坏成员报告不静默跳过（REPORT_ERROR 指名道姓）。

**4) `run_verify` —— 落盘式执行回归**

> 你说：「跑一下回归」「只跑下单相关的用例，重试 2 次」/「跑完把现场留好」
>
> 会发生：输出重定向到文件（不烧上下文），跑完建议接 `summarize_report` 归因；截图/trace/日志留在 `.playwright-artifacts/`。
> 红线：找的是**被测项目自己的** Playwright；用例失败 → isError。

**5) `cli_health` —— CLI 最小闭环验收**

> 你说：「浏览器执行层现在能用吗？验一下」/「部署完先确认能开页面」
>
> 会发生：连开页面、拿快照、截图三步；失败时报错翻译成人话并给修法（装 chromium / 换浏览器通道）。

**6) `cli_session` —— 探索页面、驱动浏览器（产物一律落盘）**

> 你说：「打开测试站首页截个图」「看一下购物车页面的结构」/「调试模式开着跑一次」（headed）
>
> 会发生：快照/截图/trace 落盘，返回只给路径与摘要（`ref` 按 snapshot 里的 e12 形态引用）。
> 红线：只接受白名单子命令；`--headed` 调试用，回归保持无头。

**7) `generate_scripts` —— PO 分层脚本生成（带生成门禁）**

> 你说：「按页面对象模式生成登录+下单的脚本」「把这个流程写成可维护的用例」
>
> 会发生：定位策略锁死（拒绝裸 XPath / nth-child）；语法 + lint ERROR 0 双门禁都过才写盘；每条用例必须有 `claims`（证明了什么）。
> 红线：占位符（`${PW}` / `{{password}}`）会被拒绝——凭据只从环境变量读。

**8) `check_standards` —— 团队规范校验**

> 你说：「我们的 AGENTS.md 测试规范写得全不全」「给我一份可以粘贴的规范模板」
>
> 会发生：四条「无论做什么任务都要遵守」的规范逐条对账（证据落盘/回归走 CLI+Skill/脚本先验证再保存/产物进制品库）；
> 缺失不阻断但明确列出；`--template` 出可粘贴模板。

**9) `orchestrate_excel` —— Excel 手工用例 → 可执行回归**

> 你说：「把 cases/regression.xlsx 这批手工用例跑起来」「先只看看映射情况，别生成」
>
> 会发生：读表（中英文列名、表头扫描）→ 自然语言步骤映射成原子步骤 → 生成门禁 → 可真跑；
> **映射不了的步骤原样报在 `unmapped` 里**——宁可不做，不能猜错。Excel 读取要 Python（缺时可用 `.csv` 兜底）。

**10) `explain_rules` —— 规则表自省（只读）**

> 你说：「PW006 为什么报？怎么关掉某条规则？」「把 lint 规则表给我看看」
>
> 会发生：规则 id、级别、判据说明与修法逐条解释；含 config / category 分组。纯查询，不改任何状态。

**11) `selfcheck` —— 服务级自检**

> 你说：「环境自检一下」「装完了，帮我确认服务是好的」
>
> 会发生：等长脱敏不变量、规则表完整性、运行器与 CLI 可用性、Python 可用性逐项过；任何一项失败都明确说明缺什么。

**12) `explore_page` —— 页面巡检（死链/坏图/表单盘点，确定性判定）**

> 你说：「巡检一下这个页面有没有死链坏图」「盘点一下表单」；两期对比：「和上一期比表单变了没有」→ 传 `diffAgainst`（上一期报告的 factsFile）
>
> 会发生：死链（HTTP ≥400）与坏图（naturalWidth=0）确定性判定，Pass/Fail + 清单；
> 表单指纹 formsHash + 两期对比（字段新增/删除/必填位变化/表单级增删）——对比是信息不是质检，不改 verdict。
> 红线：离线环境外链不可达只警告不进 Fail；生产主机要显式 `confirmProd: true`；diffAgainst 不可读时诚实报错。

**13) `nl_test_goal` —— 智能体线（说目标不说步骤）**

> 你说：「按这个目标验一遍：登录后把商品加入购物车，购物车里应看到 ITEM-A」「下单后订单状态应为待支付，帮我跑一遍」
>
> 会发生：守门（开浏览器**前**）→ LLM 规划受限计划（白名单外动作整份作废）→ 真执行真断言 → JSON `verdict`（Pass/Fail/Blocked）落盘可挂 CI；
> 定位失败两层自愈（快照按名 + LLM 挑选），自愈 LLM 调用有整次预算闸（`healLlmBudget`，默认 2）。
> 红线：断言绝不自愈；无断言判 Blocked；LLM 默认本地 Ollama，云端须显式 `PVMCP_LLM=deepseek` 且 key 只从环境变量。

**14) `collect_table` —— 分页表格采集与两期对比（确定性，不用 LLM）**

> 你说：「把这个列表页整表采下来存档」「和上次采集的对比一下新增了哪些行」「接着上次的进度继续采」
>
> 会发生：页码框/下一页两种翻页、三选止损、首见胜出归并；`rows.json` + CSV 只落盘不回灌；
> `diffAgainst` 出两期对比（新增/删除/变化/未变）；`resumeFrom` 断点续采（指纹不符拒续，`COLLECT_STALE`）。
> 红线：零行采集判 Fail；`keyIndex`/`maxPages` 只收整数；生产地址要显式 `confirmProd: true`。

### 14.3 通用约定（14 个工具一致）

- 所有失败都返回 `isError: true` 并说明原因，**绝不静默成功**；长产物一律给路径不给全文（落盘 `.playwright-artifacts/`）。
- 生产地址与危险目标在**打开浏览器之前**拒绝；测试/演练/沙箱上下文豁免误伤。
- 工具触发语简表见 [SKILL.md 触发场景](./skill/playwright-verify/SKILL.md)；说法库与对话示例见 [README「自然语言使用示例」](./README.md#自然语言使用示例)。

## 15. 发布流程（发版者）

### 15.1 为什么验收必须跑在一次性副本上

本工具的产品约定是「证据一律先落盘」——`readCases`、`cli_*`、`run_verify` 等都会把日志 / 报告 / 快照写进
`<cwd>/.playwright-artifacts/`（见 §6 安装产物布局、§11 卸载第 3 步）。回归套件以包根为 cwd 运行，
**在交付树内跑一次验收，交付树就被跑脏一次**。v1.2.0 发版时就实测到 3 个证据文件残留在交付树里，
被终查抓出后才改掉流程。发布口径只有一条：**交付树自始至终不跑任何套件**，验收全部在一次性副本上执行。

### 15.2 流程（每一步都有机械判据）

发版主命令只有一条 —— `distribute` 自带**发版门禁**（加固 H19 钉防回归）：打包收尾自动把产物
拷成一次性副本、在副本里跑 `verify-all --mode 2`（§15.3 零依赖态判据，含状态校验）、终态哈希终查、副本验后整目录删除。
**发版 = 跑 distribute，门禁不可能忘**：

```powershell
# ① 打包 + 发版门禁一条命令（逐文件哈希自校验 → 一次性副本 verify-all --mode 2 → 终态哈希终查）
node skill\playwright-verify\scripts\distribute.mjs --out <发布目录>\mcp
#   门禁行形如：
#     发版门禁: 一次性副本验收
#       副本: C:\Users\...\Temp\pvmcp-gate-xxxx\pkg
#       嵌套 verify-all: 全绿（exit 0）—— 结果：13/13 套全部通过 ✅
#       副本已删除: true
#       终态哈希终查: 0 不一致；纯净复扫 干净
#     发版门禁: 通过 ✅
#   显式跳过：--no-gate（跳过留痕）；门禁失败退出码 3 —— 发布包不可交付。
#   嵌套 verify-all 带 PV_SKIP_RELEASE_GATE=1 防递归（其内部加固 H18/H19 不再套娃）。

# ② 附加验收（建议）：装齐可选依赖后在一次性副本上跑全量 + 真实浏览器矩阵
Copy-Item <发布目录>\mcp <临时>\mcp -Recurse
Push-Location <临时>\mcp
npm ci --no-audit --no-fund                   # 装可选依赖（验收动作，非部署步骤）
node skill\playwright-verify\scripts\setup-cli-config.mjs
node mcp\test\verify-all.mjs --mode 3         # 全量判据（可选依赖必须就位，矩阵真跑 4 签名；缺依赖直接拦下不白跑）
Pop-Location
Remove-Item <临时> -Recurse

# ③ 终态终查（交付树的最后一次检查，之后不再动它）
#    - 无 node_modules、无任何 . 前缀文件 / 目录
#    - 与源码树逐文件哈希比对 0 不一致
```

门禁嵌套的 `verify-all` 跑在副本上（副本按口径无 `node_modules`）—— 零依赖整链自检，
缺可选依赖诚实 SKIP；② 的可选依赖矩阵补齐执行层面。门禁前后还会对产物树做哈希终查：
副本验收绝不碰交付树，碰了就在这里现形。

### 15.3 判据表

| 步骤 | 机械判据 | 不达标的含义 |
|---|---|---|
| 打包自校验 | 86 文件逐个哈希与源码一致、无排除项泄漏 | 排除规则写对但没生效（加固 H18 就是钉这个） |
| 发版门禁（自动） | 「发版门禁: 通过 ✅」：副本 verify-all --mode 2 全绿（含判据一致） + 终态哈希终查 0 不一致 + 副本已删除 | 产品缺陷（退出码 3，发布包不可交付）；加固 H19 钉它不失忆 |
| 副本验收（附加矩阵） | 三模式全绿，一条命令复跑一态（`verify-all --mode 1\|2\|3`，判据行自动比对）。期望断言总数 = 核心断言 mode 1 = 505、mode 2 = 560、mode 3 = 657，另 +3（源码树带 .gitattributes/.gitignore/.github/workflows/ci.yml 时 H10/H14/H22 三条存在性钉生效，纯净包里诚实 SKIP 不计数）、+26（装了部署副本时的部署段）。形态：mode 1 = 13/13、mode 2 = 14/14（+ 诚实 SKIP）、mode 3 = 14/14（+ 矩阵 2/6/1 → 4 签名）。核心数与 suites.mjs 的 coreCounts 由加固 H16 机械对账，逐套件断言数由 H22 对 suites.mjs 声明逐套对账 —— 改断言忘改声明/判据行会被拦下 | 产品缺陷（判据不满足 exit 1），或环境态不对（mode 2 要零依赖副本、mode 3 要装齐依赖，预检拦下并给修法） |
| 终态终查 | 无 `node_modules` / 无 `.` 前缀内容、与源码哈希 0 不一致 | 验收跑进了交付树，或分发之后又动过文件 |

补充：部署副本里的全量回归（§7.2）**全绿后自动清理产物目录、失败保留现场**（`--keep-artifacts`
可强制保留，供取证）。发布验收不依赖这个开关 —— 副本验完即删，产物去留无所谓；
交付树纯净靠「不进去跑」保证，不靠事后清理。
