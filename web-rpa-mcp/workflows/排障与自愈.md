# 排障与自愈

> 适用：已录制的技能回放失败、跑出空结果、卡在验证码、定时不跑。
> 原则：**先看证据（报告/截图/日志），再改流程；不要靠猜。**

## 零、先看总览（无人值守时的第一动作）

```
status_report                      # 全部流程：健康/需关注、连续失败、中断、正在执行、自愈趋势
status_report { onlyProblems: true }
```

结论是"全部流程最近一次执行正常"就到此为止，不用点开任何东西。
只有被点名的流程才需要往下走：

| 总览里的信号 | 含义 | 直接跳转 |
|---|---|---|
| "最近一次失败/被阻断" | 业务结果有问题 | 类型 A~D |
| "存在中断的执行" | 上次被强杀/断电，业务可能只做了一半 | 类型 G |
| "正在执行中"但实际没在跑 | 锁没释放 | 类型 H |
| "已配置定时但 N 小时没有新执行记录" | 定时链路断了 | 类型 E |
| "自愈 N 次"持续上升 | 页面在改版 | 类型 A → 安排重录 |

## 一、统一排查入口

```
doctor                     # 环境层：playwright / 浏览器 / 目录 / 配置
status_report              # 全流程总览（见第零节）
lock_status { flowId }     # 谁在跑、从什么时候开始、是否过期锁
run_report { flowId }      # 最近一次执行的完整报告
run_history { flowId }     # 历史趋势：失败率、自愈次数
flow_show { flowId }       # 步骤清单
flow_lint { flowId }       # 静态问题
```

报告里的关键字段：`status` / `failedStep` / `error` / `steps[].detail` / `assertions[]` / `healed[]` / `emptyGuard` / `screenshots[]`。

## 二、按失败类型分诊

### 类型 A：定位失败（元素找不到）

报告特征：错误含「定位失败」，`failedStep` 指向某一步。

判断分支：

```
是页面改版了吗？
├─ 是 → flow_show 找到那一步 → 用 record_start 只重录那一段
│        或手工 flow_step_update 补一条稳定定位符（testid/role/label）
├─ 是时序问题（元素晚出现） → flow_step_update 给该步加 timeoutMs，
│        或在前一步后插 waitFor
└─ 是 iframe 问题 → 检查步骤是否带 frame 字段（录制时会自动带上）
```

**自愈已经生效过吗？** 看 `healed` 数组：
- 有记录且判 pass → 自愈成功，新定位符已**回写进流程文件**（`flowSelfHealed: true`），下次直接命中
- 无记录且失败 → 指纹相似度低于 `run.healMinScore`（默认 0.72），说明改动太大，必须重录

### 类型 B：跑成功但结果是空的（文章头号坑）

报告特征：`emptyGuard.suspicious` 为 true，或断言 `tableNotEmpty` FAIL。

根因多半是「点到了错误的位置但流程照样走完」。修复：

1. 看 `screenshots` 里失败前后的图，确认实际停在哪一页
2. `flow_show` 核对那一步的定位符是否指对了元素
3. 用 `flow_step_update` 换成 `data-testid` 或 `role+name` 定位
4. 确认流程有非空断言（`tableNotEmpty` / `download{minLines}`）

> 这一条必须拦住：**空结果绝不能算成功**，否则定时任务会天天给你发一张空表而你不知道。

### 类型 C：卡在验证码 / 短信码

报告特征：错误含「人工接管」或超时。

修复步骤：
1. 确认该步没有被录成 `fill`（静态检查 L020/L021 会拦）
2. 在它前面插入 `humanHandoff`，例如 `{ "op": "humanHandoff", "reason": "登录验证码", "resumeWhenText": "订单日报", "timeoutMs": 300000 }`
3. 回放时必须 `headed: true`（无头模式会直接报错，不会静默卡死）
4. 定时场景不适合需要人工接管的流程 → 改为登录态持久化 + 无人值守

### 类型 D：重复提交 / 结果重复

报告特征：下游系统出现两条相同记录。

修复：
- `flow_show` 找连续两次相同提交点击 → `flow_step_delete` 删掉多余的那次
- 静态检查 L061 会在录到手滑双击时告警
- 确认提交类点击**没有**被重试（回放层默认不重试提交类点击，不要手工打开 `retryable`）

### 类型 E：定时没跑

```
schedule_list                # 看 exists / 下次运行时间 / 上次结果
schedule_run_now { flowId }  # 手工触发，验证链路
run_history { flowId }       # 看有没有产生新的执行记录
```

再看 `logs\schedule-<flowId>.log` 里 `.cmd` 包装器的原始输出。

常见原因：
- 注册时 `schtasks` 报错（`schedule_add` 返回 `stderr`）→ 权限不足，用管理员身份重试
- 任务存在但从没跑过 → 机器在计划时间处于睡眠/关机；勾选「唤醒计算机运行」或改用 `logon` 触发
- 跑了但失败 → 走类型 A~D 的排查（报告照样落在 `runs/`）

### 类型 F：告警没收到

```
notify_test                  # 先验证 Webhook 本身
notify_config                # 看 enabled / type / on 是否正确
```

再看 `logs\alerts.log` 里有没有发送记录与响应码。

注意 `on` 数组：默认只推 `failure` 和 `healed`；要成功也推，加 `success`。

### 类型 G：上一次执行被中断（interrupted）

报告特征：`run_history` 里出现 `status: interrupted`，或 `status_report` 报"存在中断的执行"。

含义：进程被强杀/断电/崩溃，**没有正常收尾**。报告不存在，只有 `running.json`。

处理：

1. `run_history { flowId }` 找到中断的 stamp，对照该流程的业务语义判断"提交类操作是否可能只做了一半"——**这是唯一需要人工确认业务状态的场景**，不要直接重跑（可能重复提交）。
2. 确认后清理标记：删除 `runs/<flowId>/<stamp>/` 目录（或用 `runs_prune`）。
3. 若是反复中断：检查机器是否被强制关机、是否有人在任务运行中 kill 进程、`run.stepTimeoutMs` 是否过短。

### 类型 H：提示"正在执行中"但实际没在跑

处理：

```
lock_status { flowId }      # 看 pid、开始时间、trigger
```

- 若 pid 对应的进程确实还在（手工在跑）→ 等它结束，别强行释放。
- 若进程已不存在或锁超过 6 小时 → 下次执行会自动清理；也可立即 `lock_release { flowId }`。
- 想彻底避免下一次撞车：确认定时任务的间隔大于流程实际耗时。

### 类型 I：出现了没预期的浏览器弹窗

报告特征：断言 `noUnexpectedDialog` 失败，detail 里有"第 N 步 confirm：... → 已取消"。

处理：这说明某个点击会弹出 confirm/alert，而流程没有声明怎么处理——**被自动取消往往等于操作没生效**。

1. 用 `flow_show` 找到第 N 步。
2. `flow_step_update { flowId, index: N, patch: { expectDialog: { accept: true } } }`（或 `accept:false`）。
3. 重跑；若该流程确实允许出现未处理弹窗，可 `config_set { patch: { run: { strictDialogs: false } } }` 降级为提示。

## 三、修完必须复验

```
flow_lint { flowId }         # 先确认阻断项清零
flow_preflight { flowId }    # 再确认定位符能命中
flow_run { flowId }          # 最后真跑一遍
```

只看「跑成功了」不够，**必须核对断言全部通过、healed 为空、截图内容正确**。

## 四、什么时候该重录而不是修

| 情况 | 处理 |
|---|---|
| 页面改版，超过 2 个步骤失效 | 重录整条流程 |
| 流程本身变了（多了审批页） | 重录 |
| 只有 1 步定位符脆弱 | `flow_step_update` 修那一步 |
| 只是超时 | 调 `timeoutMs` 或加 `waitFor` |

重录时用新名字（例如 `...v2`），跑通再删旧的，避免中断定时任务。
